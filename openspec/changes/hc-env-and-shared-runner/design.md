## Measurements

On a scratch hc core (its own `HC_SESSION` and XDG directories, hc 0.1.15):

- Every terminal carries `HC_SESSION`, `HC_TERMINAL_ID`, `HC_TERMINAL_SOCKET` and `HC_SCOPE`. `HC_SCOPE` differed between two terminals of one core; `HC_TERMINAL_SOCKET` is the core's socket path.
- A terminal started from inside terminal `t1` with that environment reported `parent: t1` and finished when `t1` was killed. Started with `HC_TERMINAL_ID`, `HC_TERMINAL_SOCKET` and `HC_SCOPE` unset, it reported `parent: null` and stayed live after `t1` was killed, with or without `--outlive-parent`. So the scrub on every hc call makes a worker no terminal's child; `hc run --outlive-parent` remains as a second guarantee.
- `HC_SCOPE` alone, without `HC_TERMINAL_ID`, changed neither what `hc ls` listed nor the parent of a terminal `hc run` started.

herdr's source sets `HERDR_ACTIVE_WORKSPACE_ID`, `HERDR_ACTIVE_TAB_ID`, `HERDR_ACTIVE_PANE_ID` and `HERDR_ACTIVE_PANE_CWD` only in the environment of a custom command (a keybinding's command). No pane's own environment carries them.

## Live checks with a real Claude Code

Claude Code 2.1.316 in a scratch hc core, with a scratch `CLAUDE_CONFIG_DIR` holding no credentials, onboarding and folder trust pre-marked, and a user `settings.json` of `{"editorMode":"vim"}`:

- **editorMode pin.** Started bare, the prompt showed `-- INSERT --` (the positive control). Started with `--settings '{"editorMode":"normal"}'`, as every claude worker is, no vim mode line appeared. The inline setting outranks the user setting, so `brief --surface hc` will not be refused for an operator who uses vim mode.
- **OSC 7501.** The same session reported `{"app":"claude-code","state":"idle"}` at turn 0 through `hc get`, so hc's status for a real worker is Claude Code's own report, not only a stub's. A full `surface launch --surface hc` worker run was not made: it writes the operator's worker ledger and needs a signed-in config.

## Decisions

- **Two directions, one predicate.** The hc scrub is the launch strip (`exec.IsLaunchStripKey`) plus a short list of keys a launch keeps (`CLAUDECODE` and a worker's identity, `FORGECTL_DRAIN_WORKER`'s containment included), so the forward direction holds by construction. The reverse check walks the hc scrub's key and prefix list, so a key added to it alone fails until a launch strips it or `launchKeepsHcDrops` records why a launch keeps it.
- **`CLAUDE_` by prefix, with a pass-list.** A review found `CLAUDE_PID`, `CLAUDE_TIMELINE_PATH` and `CLAUDE_CODE_BRIDGE_SESSION_ID` in a live session outside both name lists. Naming session variables one by one never finishes, so every `CLAUDE_` variable is dropped, from launches and hc calls alike, except `exec.ClaudeConfigEnv`: `CLAUDE_CONFIG_DIR` and the Bedrock and Vertex provider and auth-skip switches, which a harness cannot start without. Other Claude Code switches come back through the user settings `env` block, which a launched claude loads. This narrows forgectl#363's "every other value stays" for the `CLAUDE_` prefix; `CLAUDECODE` (no underscore) still stays. The test pins a fabricated `CLAUDE_FOO` as dropped.
- **`HC_SCOPE` is identity, not a server name.** It differs per terminal, so a surface launched from an hc terminal must not carry it. An hc worker gets its own terminal's value back from the trampoline, like `HC_TERMINAL_ID`.
- **The whole `HC_TERMINAL_` prefix goes at launch.** Keeping the launcher's `HC_TERMINAL_SOCKET` beside the new terminal's own `HC_TERMINAL_ID` would pair one core's socket with another core's address when the launcher's `HC_SESSION` names a different core. The trampoline puts back the new terminal's own socket (a clean absolute path, at most 1024 bytes), so both name the same core.
- **A worker gets its own terminal's socket.** The trampoline's hc branch runs for `--worktree` workers too, after the allowlist, so a worker now carries `HC_TERMINAL_SOCKET`. It names the core the worker's `HC_SESSION` already selects, so it grants nothing `HC_SESSION` does not.
- **The launcher's session id goes at launch.** A new surface is an independent session (forgectl#363); a codex or pi harness would otherwise log as the launcher in forgectl's repair log. The `CLAUDE_` prefix rule above covers it.
- **The watch holds the adapter privately.** `hcWatchSource` forwards only the read calls, so the compiler, not only the interface, keeps the watch from sending keys or closing a terminal.
- **The watch makes no ownership check.** It reads by name from a workers file or by the `cos-` prefix, has no ledger reference to compare, and never acts on a terminal. What it shares with the worker verbs is the process seam: the absolute hc path, the scrub, sealed argv, and output caps.
- **The runner's 64 KiB cap on the watch's reads.** The old client allowed 8 MiB. The sensitive runner caps every stream at 64 KiB and refuses a larger cap. On hc 0.1.15 an `hc ls --json` row was at most 259 bytes (14 terminals, 2852 bytes), so `hc ls` fits about 250 terminals before it fails as a whole and the watch falls back to per-name `hc get`. Piped `hc read` prints the screen as text (hc's help: piped output is JSON except `run`, `exec`, `read` and `file read`), and with no `--lines` it is the screen alone, about 7 KB on a full-height terminal. The screen read uses the runner's new tail mode (`exec.CaptureTail`): it reads the stream to its end and keeps the last 64 KiB, so a longer screen shows its live bottom, where the prompt and any dialog are drawn, followed by a note that it was cut. The old client also kept the end. A tail read past its cap is not an output-limit failure; `BoundedOutput.HeadDropped` says the start was dropped.
- **One hc constructor, checked at start.** The watch builds hc once. A missing hc reports `hc_unavailable` as before; an `HC_SESSION` the adapter refuses is exit 2, as it is for the worker verbs.
- **Events through a scrubbed stream.** The sensitive runner bounds each call, and `hc events` runs for as long as the view is open, so the subscription runs through `OSRunner.RunStreamingScrubbed`, which removes the same keys.
- **No second readiness signal for a forged `idle`.** A program in the worker's terminal can print an OSC 7501 `idle`. Brief already requires a second, independent signal, the screen showing the harness's empty input prompt with no dialog, and both can be forged by anything that can write to the terminal. What holds against a forger is the Escape sent before the paste, so the first key any open dialog sees is a refusal; hc's own refusal of a `blocked` terminal and `--if idle` narrow the rest. A third signal would be forgeable the same way, so none is added.
