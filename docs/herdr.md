# herdr

`internal/herdr` is forgectl's client for the herdr session the process runs in. It shells to the `herdr` CLI through `exec.Runner`. It is plumbing for the herdr commands tracked in cameronsjo/forgectl#721; the first command to use it is [`forgectl herdr organize`](commands/herdr.md). Starting a harness on a pinned server stays in `internal/surface/herdradapter`.

## Requirements

- **A herdr pane.** `CheckSession` requires `HERDR_ENV=1` and a `HERDR_SOCKET_PATH` that names an existing socket. herdr exports both into every pane it hosts. It runs no herdr command, so a read-only caller needs nothing else.
- **The `cameronsjo/herdr` fork for `tab move`.** Upstream herdr has no `tab move`, and the fork hides it from `herdr tab --help`. `CheckFork` runs `herdr tab move --help` and accepts only a usage line at the start of a line (`usage: herdr tab move ...`, matched case-insensitively so a clap-style `Usage:` also passes). Anything else returns `ErrForkRequired`. Run it after `CheckSession`, before a mutation.
- **`CheckFork` checks the CLI, not the server.** A fork CLI talking to a server still running an older binary passes the check and fails at `MoveTab` with a typed `*herdr.Error`. Restart the herdr server after upgrading the binary. The client does not translate that server error into `ErrForkRequired`: herdr's code for a missing verb could not be measured without a stock binary.
- **`CheckSession` reads the environment you give it.** Pass a lookup that matches the environment of the `Runner` you will use. If the `Runner` pins a different `HERDR_SOCKET_PATH`, the lookup must reflect that pin, or the gate checks the wrong socket.
- **Call `CheckFork` once.** It spawns `herdr` each time, and the answer does not change within a process.

## Failure shapes

| What happens | What the client returns |
|---|---|
| herdr fails (exit 1, JSON on stderr) | `*herdr.Error{Code, Message}`; match on `Code` (`workspace_not_found`, `pane_not_found`, `server_not_running`, ...). It unwraps to the `*exec.CommandError` |
| herdr exits 0 but its reply is the error envelope | the same `*herdr.Error`, unwrapping to nil because no command failed. This holds for every call that reads its reply, including `MoveWorkspace`, `FocusWorkspace`, and `FocusTab` |
| stderr is truncated, has log lines before the JSON, or is not JSON | the wrapped `*exec.CommandError` (never an `*Error` with an empty code) |
| the child was killed or timed out (exit -1), even with an error object on stderr | the wrapped `*exec.CommandError`, never an `*Error`. The runner reports a kill as `signal: killed`, not as `context.DeadlineExceeded`, so tell a timeout by checking `ctx.Err()` |
| `tab move` exits 0 with `move_result.changed=false` | `*herdr.Declined{Reason}`, for example `last_tab_in_workspace` |
| a move reply that lacks `move_result` (except an index move), lacks `changed`, or names no tab or workspace | an error; `MoveTab` fails closed |
| the response has no `result`, or a list reply lacks its list (`panes`, `tabs`, ...) | an error. A renamed key must not read as an empty session; an empty `[]` is fine |

`pane read` is the one call that prints raw text on success, so `ReadPane` returns stdout without decoding it. `exec.Runner` trims trailing newlines, so trailing blank terminal rows are not preserved. The text is whatever another pane displays: it can hold secrets typed or printed there, and terminal control sequences, so do not log it or render it to a terminal unfiltered.

`Error.Error()` and `Declined.Error()` escape control characters in herdr's text, because herdr can echo pane-controlled values (labels, titles) in a message. `Code` stays as herdr sent it; `Message` and `Reason` are stored redacted.

`MoveWorkspace`, `FocusWorkspace`, and `FocusTab` read only herdr's error envelope from a successful exit: no success reply for them has been captured. If herdr declines one quietly the way `tab move` does (`changed:false`), the client cannot report it yet.

## Shared wire decoding

`internal/herdr/wire` is the one reader of herdr's reply envelopes, shared by this client and `internal/surface/herdradapter`: the error envelope (`DecodeError`), the `result` envelope (`DecodeResult`, where a missing or null `result` fails closed), and the operand floor (`CheckOperand`: non-empty, no leading `-`, at most 64 bytes, valid UTF-8, and none of the control, bidi, or invisible characters the hub picker refuses, except ZWJ, ZWNJ, and the VS15/VS16 presentation selectors, which real labels carry in emoji and Indic or Persian text). Envelope keys (`error`, `code`, `message`, `result`) match by exact name, and so do the result's own top-level members: a case-folded `ERROR` or `Workspaces` fails closed rather than reading as herdr's key. `CheckOperand` checks the client's ids and labels, the adapter's session name (which also has to fit its own `[A-Za-z0-9._-]` charset), and the `[herdr.organize]` labels in config, so a dry run cannot promise a move the client then refuses. The adapter's workspace, tab, and pane ids go through `backend.validHerdrID` instead, which is stricter (printable ASCII only). Both packages' tests run against the captured fixtures in `internal/herdr/testdata`, including the `changed_*_envelope.json` pair, so a change to herdr's envelope shows up in both.

## Ids move

Moving a tab between workspaces renumbers the tab and its panes. `MoveResult.TabID` is the id after the move; the id you passed in is stale. It is not known whether herdr reuses a freed id, so re-list after every mutation and resolve a target by `terminal_id` immediately before acting on it. The one measured exception is an index move (`tab move --index`): it keeps every tab id, and its reply carries the workspace's tab list in the new order, so that list can stand in for a re-list as long as it holds the moved tab (`testdata/move_index.json`). `terminal_id` is stable across moves. Only `Panes()` and `Agents()` carry it (with the pane's `tab_id`); `Tabs()` and `TabGet()` do not, so join through `Panes()`.

There is no `FocusPane`. herdr's `pane focus` is directional only, so `FocusTab` is the finest focus grain available by id.

## Logging

`exec.OSRunner` logs any non-zero exit at `ERROR`, including the probe's expected exit 2. A caller that runs `CheckFork` will see one `ERROR` line per call even on success.

## Testing

Unit tests replay fixtures captured from a live session and sanitized with an allowlist (`internal/herdr/testdata`). One test checks that every fixture joins on its ids and carries no live values. To check the client against the real session, from inside a herdr pane:

```bash
HERDR_LIVE=1 go test ./internal/herdr/ -run TestLiveSession -v
```

That test is read-only.

## Worker readiness

`internal/herdr/ready` decides whether a coordinator worker's harness is at its input prompt, for `forgectl surface ready`. It is a pure function of three inputs: the pane's visible text, the agent herdr detects in the pane, and herdr's `agent_status`. A harness is ready only when no blocking screen matches, herdr names the expected agent as `idle` or `done`, and the harness's own prompt pattern matches. herdr's status alone is a hint: it reports `blocked` at an idle prompt and `done` until someone views the pane.

The predicates are TOML (`internal/herdr/ready/predicates.toml`), compiled into the binary and replaceable by `<config dir>/surface-ready.toml` (see [configuration.md](configuration.md)). Blocking patterns are broad, because a false match only makes the worker wait. Prompt patterns are strict, because a false match lets forgectl type into a dialog. The fixtures in `internal/herdr/ready/testdata` are live captures from Claude Code 2.1.289, Codex 0.160.0 and npm on herdr 0.9.1, and Pi 1.0.4 on herdr 0.9.3; rows the TOML marks `uncaptured` have no fixture yet.

The pi table (`[harness.pi]`) reads Pi 1.0.4's editor: a rule line, the input (one empty row, or rows that start in the first column), a rule line, then up to five footer rows (model, directory, and any extension status lines). Pi draws transcript rows and its dialogs indented one space, so a dialog between two rule lines does not match the editor. Pi keeps the editor on screen while a turn runs, and herdr reports `working` then, so the verdict stays not ready until the turn ends (`done` or `idle`). Its blocking rows are the project trust dialog (`Trust project folder?`, shown at start when the folder has `.pi` settings or resources) and the `↑↓ navigate  enter select` footer every pi selector shares. Pi has no tool approval prompt: in the capture, a Bash call ran without one.

Reading the worker's pane is not this package's job. `internal/surface/herdradapter`'s `WorkerScreen` does it on the pinned server, through the sensitive runner (`herdr.screen-read` and `herdr.pane-status`), and only for a pane forgectl owns: the workspace must carry forgectl's ownership marker, the pane must be the root pane its create response named, and `pane get` must place that pane in that workspace. A workspace that is provably absent returns `ErrWorkerGone`; any other failure returns `ErrScreenUnreadable`, which is never a verdict about the worker.

## Briefs, waits and reports

A worker's first brief goes in at launch. `surface launch --brief` appends it to the harness argv after `--`, and the trampoline socket carries that argv to the pane, so the brief is never typed into a running TUI. The brief then stays in the harness's process arguments for the whole session, where `ps -ww` can read it, so a launch brief must not hold a secret. Every harness treats what follows `--` as the prompt: Claude Code 2.1.289 answered `-- mcp` as a prompt rather than running the `mcp` subcommand, and Codex 0.160.0 and Pi 1.0.4 took `-- --help` as one. Pi still reads an argument that starts with `@` as a file to attach, after `--` too (`pi -- '@README.md say OK'` exits `File not found`), so a pi launch refuses a brief that starts with `@`.

`surface brief` types the follow-ups. It writes through `TypeText` (`herdr.send-text`) and `PressEnter` (`herdr.send-keys`). Each call re-runs the ownership check `WorkerScreen` uses, so forgectl types only into the root pane of a workspace it owns. Three herdr and Claude Code facts shape it, measured on herdr 0.9.1 and Claude Code 2.1.289:

- `pane send-text` does not honour `--`; it types the `--`. A text starting with `-` types correctly without one. The sensitive runner still refuses such an operand, so `CheckBrief` refuses a typed brief that starts with `-`.
- Claude Code collapses typed text between 700 and 900 characters into `[Pasted text #N]`, which the read-back cannot compare, so a typed brief is capped at 600 characters with its report instruction.
- herdr reported `working` within 0.4 s of Enter, and `done` when the turn ended.

Every brief carries a random 12-character marker, recorded in the ledger row before the brief is sent. The brief spells the REPORT line out in words, so its own echo never matches `REPORT <marker>:`. `worker.FindReport` also takes only report lines below the last line that names the marker. A report is still the worker's claim, and the coordinator checks it against git.

`surface wait` does not compare screen text for stability, because a harness's status line and any mod drawing above the prompt change every second. It needs the ready verdict to hold for `--settle`, plus one of: a `working` status seen during the wait, the report on screen, or `--quiet` at the prompt.

## What a claude worker loads

A claude worker is a full harness (ADR-0010, 2026-10-08 amendment): it loads what an ordinary session started by the operator loads. That is the operator's user settings and their allow rules, plugins, skills and hooks; MCP servers, plugin-provided ones included (herdr-bridge can drive any herdr pane); Claude in Chrome; `CLAUDE.md` and rules; project auto-memory; and the branch's own `.claude/settings.json` and `.mcp.json`. Nothing is denied: a worker can message other sessions with `SendMessage`. forgectl adds only the following:

- **No `--ide`:** the worker does not ask to connect to the operator's editor.
- **An environment allowlist:** a worker inherits only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `COLORTERM`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, `CLAUDE_CONFIG_DIR`, the CA and config-home paths (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `CODEX_HOME`, `XDG_CONFIG_HOME`) and `SSH_AUTH_SOCK`, plus herdr's pane ids. With `--profile <name>`, `CLAUDE_CONFIG_DIR` is set to that [`[surface.profiles]`](configuration.md#worker-profiles) entry's `config_dir`, over the inherited value and the launch profile's `env`; no other variable is added. `SSH_AUTH_SOCK` is a deliberate grant: the remotes push over SSH, so it stays while workers run as the operator (ADR-0010, 2026-10-06 amendment; forgectl#1134 lists what would replace it). When the launcher is a Claude Code session, its own handles (the cross-session messaging socket and token, the herdr and cmux sockets) stay out of the worker's environment, so a nested `claude` behaves as a fresh session. The operator's user settings `env` block applies again, because user settings load. This is about a clean environment, not containment: a worker has `SendMessage` and herdr-bridge directly.
- **`--settings`:** sets `useAutoModeDuringPlan: false` (forgectl#1060), so a `plan` worker's shell commands prompt rather than going to the classifier.
- **Model:** the matched launch profile's, unless `--model <name>` replaces it for this worker; effort is derived again from the new model, as a `--harness` override does. Only the `sonnet`, `opus` and `fable` aliases map to an effort, so a full model id (`claude-opus-5-5`) or another alias (`haiku`) leaves effort empty and Claude Code's own setting applies. The value is a plain token (letters, digits, `.`, `-`, `_`, `[`, `]`, at most 64 characters, not starting with `-`), so it cannot become a flag.
- **Permission mode:** `[launch.worker] permission_mode`, `acceptEdits` by default; `auto` is allowed (ADR-0010, 2026-10-07), and sends the tool calls the mode does not approve on its own (reads and in-worktree edits are approved) to Claude Code's classifier instead of the operator. `dontAsk` and `bypassPermissions` are refused.
- **An allow list, for `acceptEdits` workers:** `--settings` adds `go test`, `go build`, `make`, `git add`, `git commit`, `git push`, `gh pr create` and `gh pr view` (each as `Bash(<command> *)`). The operator's own allow rules load in every mode as well and usually reach further: with `Bash(gh:*)`, a worker runs `gh pr merge` or `gh api` writes without a prompt. Whether a command prompts depends on those rules, not on this list. A prefix rule cannot see where a push goes, so only a repository ruleset refuses a push to `main` (forgectl and cadence require a pull request).

A unit test pins the argv, the settings JSON and the environment allowlist. What a worker loads beyond that is whatever the operator's own configuration loads, and changes when it does.

## Worker harnesses

A worker runs claude, codex, or pi: the harness the matched launch profile names, or `--harness` on `surface launch` and `surface enqueue`. Each is an ordinary session of that harness (ADR-0010, 2026-10-08 amendment); forgectl adds no isolation and no deny rules for any of them. All three take the environment allowlist above, no harness args, and the brief after `--`.

- **claude:** the section above.
- **codex:** `--sandbox` and `--ask-for-approval` from the worker profile, capped at `workspace-write` and `on-request`; `--model` when one is set.
- **pi:** `pi [--model <name>] -- <brief>`, and nothing else. Pi has no permission or sandbox flag, so a pi worker runs with pi's own config and extensions, as a claude worker runs with the operator's settings. The worker floor still refuses harness args, and still clears `allow_danger` and `add_dir`.

`--profile` sets `CLAUDE_CONFIG_DIR`, so it is refused for codex and pi. Only a claude worker gets a `--session-id` and a transcript path.

## Where a worker branch starts

A `--worktree` branch that does not exist yet starts at the head of the repository's GitHub default branch (forgectl#1061), not at the checkout's `HEAD`, which is often stale or on another branch. forgectl reads the branch and its head commit from the GitHub API, fetches that branch from `origin`, checks the fetched commit is the one GitHub named, and passes the hash to `git worktree add`. Only an `origin` URL whose host is `github.com` or `ssh.github.com` counts as GitHub; any other origin, an SSH host alias for GitHub included, starts the branch at the checkout's `HEAD` as before. A failing GitHub call fails the launch rather than falling back. An existing branch is checked out as it is, and needs no GitHub call.

This is a correctness fix, not a security control. Workers in one repository share its `.git` and are mutually trusting (ADR-0010): an earlier worker can change what the next one starts from.

## Listing and closing workers

`surface list` probes each ledger row's workspace through `Adapter.Probe`, the same lookup `Close` uses: the server incarnation must match the reference, the listing must be complete, and the workspace must carry forgectl's ownership marker. The incarnation is the session's socket, not the way the session was chosen: no `HERDR_SESSION` and `HERDR_SESSION=default` select one server, so a plain CLI reads and closes the workers the drain launched with the pin. A reference from the default session is refused outright in any other named session, and one from another named session fails the incarnation check. A workspace missing from that listing is `gone`. Any herdr error is `unreadable`, and so is an identity mismatch: after a herdr restart, or when a workspace id now names a workspace without forgectl's marker, nothing proves forgectl's own workspace gone. `--orphans` keeps the rows `close` should act on: a `gone` workspace, or any stage other than `launched` (`failed`, `closed`, or a launch stopped at `pending` or `worktree`). A launch at `pending` or `worktree` for less than ten minutes may still be running, so it is never an orphan, and `close` refuses it.

A claude worker is started with a forgectl-generated `--session-id`, and its row records the transcript path Claude Code writes: `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<slug>/<id>.jsonl`, where `CLAUDE_CONFIG_DIR` is the worker's own (a `--profile` launch's is the profile's `config_dir`), where the slug is the worktree path with every character other than an ASCII letter or digit replaced by `-`. The path comes from the environment the harness was started with. Codex and pi workers have neither field.

`surface close` closes the workspace first, so the harness stops before its worktree is judged. It refuses, touching nothing, when the close comes back unreadable, failed, or an identity mismatch. A row at stage `closed` skips herdr: an earlier close already closed its workspace. It then removes the worktree only when `git status --porcelain --ignored` is empty, HEAD is on a branch, the branch has nothing beyond its upstream (or, with none, beyond the commit the worktree started at), and no stash entry names the branch. The path comes from `git worktree list`, not the ledger, and `git worktree remove` runs without `--force`, so git refuses on its own if a tracked or untracked file changed after the checks. Git does delete ignored files, so an ignored file written after the check is lost; closing the workspace first stops the harness that would write one. The ledger row is removed or marked `closed` only if it is still the row close read, so a launch that reused the name meanwhile is left alone. The branch is never deleted. A kept worktree leaves the row at stage `closed`; a later close retries it.

`surface close --dry-run` previews that decision and changes nothing. It runs the checks that need no write: the launch-in-flight refusal, the ledger stage, and the read-only worktree inspection. herdr is not asked, so a workspace close would close reads `would-close`, and the preview cannot say whether herdr would refuse. It prints `workspace` (`would-close`, `closed-earlier`, `none`, `refused`), `worktree` (`would-remove`, `would-keep`, `gone`, `untouched`), `kept_because`, and `would_forget`; with `--json`, `{name, branch, dry_run, refused, workspace, worktree, kept_because, would_forget, reason, note}`. Text mode prints a `refused=` line too. Where close would refuse, the preview prints the same lines (or the same JSON object) and then exits 1, with the reason as the error, so `close --dry-run && close` stops where close would. The preview and the real close share one decision for the workspace and one for the worktree; only what needs herdr, or a write, differs. The worktree inspection runs `git status` with `--no-optional-locks`, so the preview takes no `index.lock` and rewrites no index. A worktree in the middle of a rebase or bisect can list as a detached HEAD, which blocks removal (`would-keep`).

`surface launch --dry-run` previews a launch: it checks that the backend is on `PATH`, the target resolves, the harness profile builds (and passes the binary policy), and, for `--worktree`, that the name is free in the ledger and the branch and worktree path are usable. It then prints what it would create and creates none of it: no worktree, `.claude` directory, branch, ledger row or surface, and no call to the backend. It never prints the harness path, arguments, environment or brief. A new branch reads as `branch_from=new`; its base commit is read from GitHub when the launch runs, not by the preview. The preview refuses a local branch that another worktree (the main checkout included) has checked out, which git would refuse. It cannot see any other refusal git makes only when `git worktree add` runs, so a clean preview is not a promise. `--json` (which needs `--dry-run`) prints `{dry_run, surface, name, target, harness, worker}`, with `worker` (`{repo, worktree, branch, branch_from, ledger_row, brief, posture}`) only for `--worktree`. `posture` shows the worker posture the launch would use, so an operator can confirm `auto` took effect: each field the harness takes (claude `permission_mode`; codex `sandbox` and `approval_policy`; pi none) maps to `{value, source}`, where `source` is `default` (the built-in worker value), `launch.worker`, or `repo-profile` (a stricter matched project block). The text preview prints `permission_mode=auto` and `permission_mode_source=launch.worker` lines.

## Queue

`surface enqueue --repo <path> --name <slug> --brief <file>` adds a brief to the machine's queue, `$XDG_STATE_HOME/forgectl/surface/queue.json`, for the drain (`surface drain`, below) to launch as a worker. `--harness claude|codex|pi` (default `claude`) is stored on the row, and the drain launches the row with it; a row written before the field existed runs claude. The file is written like a ledger: through the pinned surface directory, opened without following a symlink, 0600 in a 0700 directory, under an flock on `queue.lock`, and replaced by an atomic rename. A file with an unknown version, field or state is refused, not rewritten. `name` is unique across the whole queue. The brief file is read once and stored as text: at most 64 KiB, checked as a launch brief, and it may not start with `@`. `--profile <name>` and `--model <name>` choose the worker's [`[surface.profiles]`](configuration.md#worker-profiles) entry and model, as on `surface launch`: the profile for claude only, the model for every harness (its `--model`); the row stores the profile's name (`main` as none), never its path, and an unknown name is refused at enqueue. Enqueueing a name again with the same brief, harness, profile and model changes nothing and prints the row's state; a different brief or repository is refused, naming both brief hashes, and so is another harness, profile or model. The document stays under 768 KiB, and an enqueue past that is refused before anything is written. A row in a terminal state (`reported`, `failed`, `closed`, `expired`) drops its brief text and keeps `brief_sha256`. `surface dequeue <name> [--json]` removes a row unless its worker may be live (`claimed`, `launched`, `needs-you`), which needs `surface close` first; after a dequeue the name can be enqueued again, which is how a `failed` row is retried. `surface queue [--json]` lists each row's state and how long it has been in it, and never prints brief text. The drain claims a row by moving it from `queued` to `claimed` under the queue lock and writing its `launch_id`, so of two claimers exactly one wins.

## Intake

`surface intake gh --repo <path>` turns open GitHub issues that carry an eligible label into queue rows, so the drain works them. The label is the request. Removing it stops later intake runs from taking the issue; a row already queued stays, and launches, until `forgectl surface dequeue <name>` removes it. The operator or a coordinator session runs intake by hand; the drain never calls GitHub for it.

A drain worker runs as the operator with the operator's allow rules (ADR-0010), and an issue's text becomes its brief, so intake takes an issue only when the operator trusts that text. Every check below reads one GraphQL response, and the body checked is the body queued:

- **Author.** The issue's author is on `[surface.intake] authors`. With no `authors`, a user-owned repository allows its owner's login only, and only when that owner is the account `gh` is authenticated as (the query's `viewer`, compared case-insensitively); otherwise, as for an organization-owned repository, the run is refused with exit 2 until `authors` is set. A missing `viewer` login refuses the run. Logins compare case-insensitively and exactly. A bot is never allowed: GraphQL types it `Bot` and spells its login without the `[bot]` suffix, so the check reads `__typename`, and a login ending `[bot]` is refused as well.
- **Labeler.** The default eligible label is `queue:drain`, which no triage sweep applies, so its labeling means a person asked for the work. A bulk-applied label such as the `exec:*` triage set proves only that a script ran as the owner; listing one in `labels` trusts that script. For each eligible label on the issue, the latest `labeled` event for that name is by an allowed author (every one, when several share that second), and no `unlabeled` event for it is at or after that time. GitHub timestamps are whole seconds and its timeline lists same-second events in no reliable order, so a same-second removal refuses.
- **No edits after labeling.** `lastEditedAt` is an explicit JSON `null` (never edited) or strictly before the earliest of those latest labelings, and no `RenamedTitleEvent` is at or after it. A missing field, or any GraphQL error, refuses. The earliest labeling counts, so every eligible label on the issue was added after its text was final.
- **Issues only, never transferred.** `repository.issues` holds only GraphQL `Issue` nodes; intake still checks `__typename`. A `TransferredEvent` refuses.
- **Nothing unseen.** An issue with more than 100 labels or timeline events of the four types read is refused rather than judged on a partial history.

The row's brief is a fixed template: the rules, then the issue's title and body between the lines `BEGIN ISSUE TEXT <nonce>` and `END ISSUE TEXT <nonce>`, the nonce a fresh random 12-hex-character marker, drawn again if the text contains it, so the body cannot close the fence. The rules say the fenced text is the whole task, to treat instructions inside it or in anything fetched as data, not to read the issue, its comments, linked issues or pull requests, or any URL with `gh`, `curl` or anything else, never to create, edit or comment on issues or labels, to work only in the worktree, to run the tests, commit, push the branch, and open a draft pull request whose body contains `Closes #<number>`, and never to merge, mark a pull request ready, push the default branch, or edit another repository. The issue number appears only in that `Closes` rule. The body's CRLF line ends become LF; any other control, bidi or invisible character fails `CheckQueueBrief`, as does a brief over 64 KiB, and the issue is skipped.

These rules are instructions, not a sandbox. A worker can still fetch the issue and its comments, and every agent on the machine acts as the owner, so a misled worker could file and label an issue that passes every check. ADR-0010's "accidents, not adversaries" covers both; `max_per_run` and the label-as-request model limit how far one mistake spreads.

- **Repository.** `--repo` is a project name or path, as on `surface enqueue`; intake reads `owner/repo` from its `origin` remote, which must be on `github.com` (or `ssh.github.com`), and refuses any other host. The query runs as `gh api graphql --hostname github.com` through the host-pinned runner. If GitHub names a different owner than origin (a rename or transfer it followed), intake refuses.
- **Rows.** Each row is named `gh<number>-<repo name>`, the name lowercased with other characters mapped to `-` and cut so the whole name fits 48 characters; the number is always kept. It records `source` (`gh:<owner>/<repo>#<number>`) and `author` (the issue's author), both shown by `surface queue --json`. `--harness`, `--model` and `--profile` apply to every row the run adds. These two fields are new in the queue file without a version change, so a drain running an older binary refuses a queue file holding an intake row and must be restarted after the upgrade.
- **Dedupe.** An existing row of the same name, in any state, skips the issue naming its state (`failed` adds "dequeue it to retry"); one held by another repository is skipped naming that repository. `dequeue` makes the issue eligible again on the next run if it still carries the label.
- **Per issue.** Every refusal or skip is reported with the issue number and reason, and the run goes on. A full queue stops the run and exits 1; a GitHub read failure does too. `[surface.intake] max_per_run` (default 5) caps the rows one run adds; at most 20 pages of 25 issues are read per run.
- **Preview.** `--dry-run` reads GitHub and the queue and writes nothing. `--json` prints `{dry_run, repo, github, authors, labels, enqueued: [{number, name, source, author, brief_sha256}], skipped: [{number, name, source, author, reason}], stopped}`; with `--dry-run`, `enqueued` is what would be queued.
- **Config.** `[surface.intake]`: `authors` (GitHub logins), `labels` (default `["queue:drain"]`; `--label` narrows to one of them), `max_per_run` (1 to 50, default 5). A bad value, or an unknown key such as a misspelled `lables`, makes the config file invalid at load, and intake refuses it again; it never falls back to a default.

Exit 0: the run finished, whatever it skipped. Exit 1: the queue filled or GitHub could not be read, after queueing what came before. Exit 2: a usage or setup error.

## Drain

`surface drain start` starts a detached process that launches the queue's rows as herdr workers, each with its row's harness, and watches them. It is the one unattended launcher: it never types into a pane and never answers a prompt; a worker stopped at a prompt waits for the operator in its own pane.

- **Start and stop.** `start` resolves the herdr session the way `surface launch` does and starts `forgectl surface _drain` with `Setsid`, `/dev/null` stdin, this command's environment, and `HERDR_SESSION` pinned to that session; the child refuses to start if herdr or the session resolve differently (checked at startup only; later ticks resolve `herdr` from the same inherited `PATH`). Before it starts the child, `start` creates and removes one private run directory where every launch makes its own (`os.TempDir()`, from `TMPDIR`), and exits 2 naming `TMPDIR` when it cannot: an unset `TMPDIR` on macOS is `/tmp`, a symlink. `start` waits up to 5 s for `drain.json` to show `running` or `paused`, otherwise exits 1 printing the last events line. A second `start` while a drain holds `drain.lock` (flock, `LOCK_EX|LOCK_NB`) exits 1 naming the holder's pid and start time. `stop` sends `SIGTERM` only when `drain.json` records a non-zero process start time equal to the live process's (`internal/procstart`); the drain finishes its current step (a launch in progress completes) and exits, writing `stopped`. A crash releases the flock, and the next `start` takes over.
- **Files.** `drain.lock`, `drain.json` (status, replaced atomically each tick) and `drain-events.jsonl` (appended; renamed to `.1` when it would pass 1 MiB, replacing the previous `.1`) sit beside `queue.json` and go through the same pinned directory and verified open: 0600 files in a 0700 directory, no symlink followed.
- **Config.** `[surface.drain]`: `interval` (default `"15s"`, at least `5s`), `cap` (default 3, at most 10), `per_repo` (default 1), `notify` (default `true`), `idle_minutes` (default 10). The drain reloads the config file every tick. A file that does not load, or an out-of-range value, pauses claiming with the reason in `drain status` and the events; it never falls back to a default. Watching continues with the last valid values.
- **Slots.** A row in `claimed` holds a slot, and so does any row whose own ledger row (same `launch_id`) is at `pending`, `worktree` or `launched`, whatever the queue says: a `failed` row with a live worker holds its repo's slot until `surface close`. A `reported` row frees its slot even while its worker runs (a worker can print its report early; P4 checks reports against git).
- **Each tick**, in order: claimed rows left by a launch that is no longer running are settled from their ledger row (none or another `launch_id`, or created nothing → `queued` with no attempt; `pending` or `worktree` → `failed` naming the worktree; `launched`, `failed`, `closed` → the same). Each `launched` or `needs-you` row gets one screen read: its REPORT line → `reported`; a blocking screen → `needs-you`, notified once; any other verdict while `needs-you` for a blocking screen → `launched`; at the prompt with no report for `idle_minutes` → `needs-you` (`idle without report`), which clears once the worker is working again; ledger row `closed` or removed → `closed`; ledger row `failed` or the workspace gone → `failed` (a gone workspace's row still holds its slot, and its last error says to run `surface close <name>`); an unreadable pane or ledger leaves the row as is and records one event. A `reported` or `failed` row whose own ledger row is then closed or removed by `surface close` → `closed`; a row failed with nothing of its launch left (a refused row, a taken name, three empty attempts) drops its `launch_id`, so this never mistakes another launch for its close. Rows `queued` for more than 7 days → `expired`. Then, unless paused, the oldest `queued` rows are claimed one at a time (`launch_id` and the herdr session written under the queue lock) and launched outside it through the in-process worker launch, with the row's harness, branch `worker/<name>`, after re-checking the row's repo (clean, absolute, still its own top), brief (`CheckQueueBrief`), brief hash and harness (claude, codex or pi; a profile only with claude). Terminal rows older than 30 days are removed, each only if it is still the row read.
- **Profile and model.** A row's profile name is resolved from the config file the tick loaded, at launch, and its `config_dir` becomes the worker's `CLAUDE_CONFIG_DIR`; the row's model replaces the launch profile's. A name the config does not define is a launch-config failure before anything is created: the row goes back to `queued` with no attempt counted and claiming pauses until the next `drain start`. A row whose stored profile name or model is not the right shape is refused before launch, like a bad brief.
- **Session cap (claude-slots).** `_drain` resolves `claude-slots` on `PATH` once at startup and records it in `drain.json` as `claude_slots_path`. Before each claude launch (after the claim and the row's re-check), it runs `claude-slots check <N>`, capped at 5 s, with the drain's environment. N is 1 plus the launches this tick has already made, since a session launched moments ago may not be registered yet: with one slot free and three rows planned, only the first launches. A check cut short because the drain is stopping launches nothing and records no event. Exit 0 launches. Exit 1 puts the row back to `queued` with no attempt counted and its `launch_id` dropped, sets `last_error` to the tool's first output line, and claims nothing more that tick; one `slots-held` event names the reason when the drain enters that condition, not one per tick (a tick with nothing to claim ends the condition, so a later hold records a new event), and the claim and requeue write no `state` events. Any other exit code, a run that fails to start, or a timeout launches as if the tool were missing, with one `error` event per condition. A codex or pi row is not a claude session and launches without the check. When `claude-slots` is not on `PATH` at startup, the drain records one `note` event ("claude-slots not found; launching without the session cap") and launches as before. A held claude row does not block codex or pi rows in the same tick, which are not claude sessions; later claude rows that tick are skipped. The tick plans rows oldest first up to `cap`, so with `cap = 1` a held claude row still holds the only planned slot. Every launch in a tick counts toward the slots the next claude check asks for, which errs strict.
- **Launch failures.** A failure that created nothing goes back to `queued` with one more attempt, and to `failed` at the third. A failure after anything was created (worktree, workspace, recovery tag) is `failed` at once, naming the error, worktree and ledger stage; so is a name the ledger already holds. The way back is `surface close`, then `dequeue` and `enqueue`. A GitHub auth failure, herdr unreachable, or a launch configuration that cannot build a worker (the worker posture, the harness profile, a harness binary found only on `$PATH`), or a private run directory the environment cannot provide (a `TMPDIR` that is a symlink, too long, or shared without the sticky bit), pauses claiming. The row goes back to `queued` with no attempt counted when the failure created nothing, and is `failed` naming its worktree otherwise. A herdr pause is re-checked each tick (the drain asks herdr's readiness before claiming); an auth or launch-config pause lasts until the next `drain start`. The drain never passes `--allow-path-binary`: name each harness's binary in `[launch.defaults]` (`binary_path`, `codex_binary_path`, `pi_binary_path`) or its `FORGECTL_*_BIN` variable.
- **Status and events.** `drain status [--json]` prints `running`, `paused` (with the reason), `stopped`, or `stale` (last tick older than 3 intervals), the pid, start time and herdr session, counts per state, the rows in `needs-you` or `failed` with their last error, and `held_slots` with the names of the rows `holding` them, so a queue held back by failed rows whose workers are still live is explainable. `drain events [--since <seq>] [--json]` prints `{v, ts, seq, kind, name, repo, state, attempt, error}` lines, kinds `start`, `stop`, `state`, `pause`, `resume`, `unreadable`, `error`, `slots-held`, `note`; `seq` counts from 1 in each drain process, so `--since` reads only the latest run.
- **Needs-you notifications.** When a row enters `needs-you` and `[surface.drain] notify` is on, the drain does two things, once per entry. On macOS it posts one notification, title `forgectl: <name> needs you`, body the reason (`blocked: <screen>` or `idle without report`), through `osascript` with both as arguments, never as script text. It also puts the worker's own pane in herdr's needs-you state (`pane report-agent --source forgectl-drain --state blocked`, message `forgectl: <name> needs you — <reason>`). That pane comes from the worker's ledger ref, on the drain's pinned herdr session, and only after the same checks a screen read makes: the workspace carries forgectl's marker, the pane is the root pane the create named, and herdr places it in that workspace. The drain's own `HERDR_PANE_ID` is never used. A pane that fails a check is left alone and the macOS notification still goes out. When the row leaves `needs-you`, the drain releases the `forgectl-drain` state on the pane, whatever `notify` says, so turning it off never strands a marked pane; a closed workspace has nothing to release. A failed notification or release never fails the tick: it is one `error` event per entry or exit, not one per tick. The one `notify` switch covers both halves; the desk's `notify_macos` and `notify_herdr` do not apply to the drain.
