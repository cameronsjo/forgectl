# herdr

`internal/herdr` is forgectl's client for the herdr session the process runs in. It shells to the `herdr` CLI through `exec.Runner`. It is plumbing for the herdr commands tracked in cameronsjo/forgectl#721; the first command to use it is [`forgectl herdr organize`](commands/herdr.md). Starting a harness on a pinned server stays in `internal/surface/herdradapter`.

## Requirements

- **A herdr pane.** `CheckSession` requires `HERDR_ENV=1` and a `HERDR_SOCKET_PATH` that names an existing socket. herdr exports both into every pane it hosts. It runs no herdr command, so a read-only caller needs nothing else.
- **The `cameronsjo/herdr` fork for `tab move`.** Upstream herdr has no `tab move`, and the fork hides it from `herdr tab --help`. `CheckFork` runs `herdr tab move --help` and accepts only a usage line at the start of a line (`usage: herdr tab move ...`, matched case-insensitively so a clap-style `Usage:` also passes). Anything else returns `ErrForkRequired`. Run it after `CheckSession`, before a mutation.
- **`CheckFork` checks the CLI, not the server.** A fork CLI talking to a server still running an older binary passes the check and fails at `MoveTab` with a typed `*herdr.Error`. Restart the herdr server after upgrading the binary. The client does not translate that server error into `ErrForkRequired`: herdr's code for a missing verb could not be measured without a stock binary.
- **`CheckSession` reads the environment you give it.** Pass a lookup that matches the environment of the `Runner` you will use. If the `Runner` pins a different `HERDR_SOCKET_PATH`, the lookup must reflect that pin, or the gate checks the wrong socket.
- **Call `CheckFork` once.** It spawns `herdr` each time, and the answer does not change within a process.

## Failure shapes

| What happens | What the client returns |
|---|---|
| herdr fails (exit 1, JSON on stderr) | `*herdr.Error{Code, Message}`; match on `Code` (`workspace_not_found`, `pane_not_found`, `server_not_running`, ...). It unwraps to the `*exec.CommandError` |
| herdr exits 0 but its reply is the error envelope | the same `*herdr.Error`, unwrapping to nil because no command failed. This holds for every call that reads its reply, including `MoveWorkspace`, `FocusWorkspace`, and `FocusTab` |
| stderr is truncated, has log lines before the JSON, or is not JSON | the wrapped `*exec.CommandError` (never an `*Error` with an empty code) |
| the child was killed or timed out (exit -1), even with an error object on stderr | the wrapped `*exec.CommandError`, never an `*Error`. The runner reports a kill as `signal: killed`, not as `context.DeadlineExceeded`, so tell a timeout by checking `ctx.Err()` |
| `tab move` exits 0 with `move_result.changed=false` | `*herdr.Declined{Reason}`, for example `last_tab_in_workspace` |
| a move reply that lacks `move_result` (except an index move), lacks `changed`, or names no tab or workspace | an error; `MoveTab` fails closed |
| the response has no `result`, or a list reply lacks its list (`panes`, `tabs`, ...) | an error. A renamed key must not read as an empty session; an empty `[]` is fine |

`pane read` is the one call that prints raw text on success, so `ReadPane` returns stdout without decoding it. `exec.Runner` trims trailing newlines, so trailing blank terminal rows are not preserved. The text is whatever another pane displays: it can hold secrets typed or printed there, and terminal control sequences, so do not log it or render it to a terminal unfiltered.

`Error.Error()` and `Declined.Error()` escape control characters in herdr's text, because herdr can echo pane-controlled values (labels, titles) in a message. `Code` stays as herdr sent it; `Message` and `Reason` are stored redacted.

`MoveWorkspace`, `FocusWorkspace`, and `FocusTab` read only herdr's error envelope from a successful exit: no success reply for them has been captured. If herdr declines one quietly the way `tab move` does (`changed:false`), the client cannot report it yet.

## Shared wire decoding

`internal/herdr/wire` is the one reader of herdr's reply envelopes, shared by this client and `internal/surface/herdradapter`: the error envelope (`DecodeError`), the `result` envelope (`DecodeResult`, where a missing or null `result` fails closed), and the operand floor (`CheckOperand`: non-empty, no leading `-`, at most 64 bytes, valid UTF-8, and none of the control, bidi, or invisible characters the hub picker refuses, except ZWJ, ZWNJ, and the VS15/VS16 presentation selectors, which real labels carry in emoji and Indic or Persian text). Envelope keys (`error`, `code`, `message`, `result`) match by exact name, and so do the result's own top-level members: a case-folded `ERROR` or `Workspaces` fails closed rather than reading as herdr's key. `CheckOperand` checks the client's ids and labels, the adapter's session name (which also has to fit its own `[A-Za-z0-9._-]` charset), and the `[herdr.organize]` labels in config, so a dry run cannot promise a move the client then refuses. The adapter's workspace, tab, and pane ids go through `backend.validHerdrID` instead, which is stricter (printable ASCII only). Both packages' tests run against the captured fixtures in `internal/herdr/testdata`, including the `changed_*_envelope.json` pair, so a change to herdr's envelope shows up in both.

## Ids move

Moving a tab between workspaces renumbers the tab and its panes. `MoveResult.TabID` is the id after the move; the id you passed in is stale. It is not known whether herdr reuses a freed id, so re-list after every mutation and resolve a target by `terminal_id` immediately before acting on it. The one measured exception is an index move (`tab move --index`): it keeps every tab id, and its reply carries the workspace's tab list in the new order, so that list can stand in for a re-list as long as it holds the moved tab (`testdata/move_index.json`). `terminal_id` is stable across moves. Only `Panes()` and `Agents()` carry it (with the pane's `tab_id`); `Tabs()` and `TabGet()` do not, so join through `Panes()`.

There is no `FocusPane`. herdr's `pane focus` is directional only, so `FocusTab` is the finest focus grain available by id.

## Logging

`exec.OSRunner` logs any non-zero exit at `ERROR`, including the probe's expected exit 2. A caller that runs `CheckFork` will see one `ERROR` line per call even on success.

## Testing

Unit tests replay fixtures captured from a live session and sanitized with an allowlist (`internal/herdr/testdata`). One test checks that every fixture joins on its ids and carries no live values. To check the client against the real session, from inside a herdr pane:

```bash
HERDR_LIVE=1 go test ./internal/herdr/ -run TestLiveSession -v
```

That test is read-only.

## Worker readiness

`internal/herdr/ready` decides whether a coordinator worker's harness is at its input prompt, for `forgectl surface ready`. It is a pure function of three inputs: the pane's visible text, the agent herdr detects in the pane, and herdr's `agent_status`. A harness is ready only when no blocking screen matches, herdr names the expected agent as `idle` or `done`, and the harness's own prompt pattern matches. herdr's status alone is a hint: it reports `blocked` at an idle prompt and `done` until someone views the pane.

The predicates are TOML (`internal/herdr/ready/predicates.toml`), compiled into the binary and replaceable by `<config dir>/surface-ready.toml` (see [configuration.md](configuration.md)). Blocking patterns are broad, because a false match only makes the worker wait. Prompt patterns are strict, because a false match lets forgectl type into a dialog. The fixtures in `internal/herdr/ready/testdata` are live captures from Claude Code 2.1.289, Codex 0.160.0 and npm on herdr 0.9.1, and Pi 1.0.4 on herdr 0.9.3; rows the TOML marks `uncaptured` have no fixture yet.

The pi table (`[harness.pi]`) reads Pi 1.0.4's editor: a rule line, the input (one empty row, or rows that start in the first column), a rule line, then up to five footer rows (model, directory, and any extension status lines). Pi draws transcript rows and its dialogs indented one space, so a dialog between two rule lines does not match the editor. Pi keeps the editor on screen while a turn runs, and herdr reports `working` then, so the verdict stays not ready until the turn ends (`done` or `idle`). Its blocking rows are the project trust dialog (`Trust project folder?`, shown at start when the folder has `.pi` settings or resources) and the `↑↓ navigate  enter select` footer every pi selector shares. Pi has no tool approval prompt: in the capture, a Bash call ran without one.

Reading the worker's pane is not this package's job. `internal/surface/herdradapter`'s `WorkerScreen` does it on the pinned server, through the sensitive runner (`herdr.screen-read` and `herdr.pane-status`), and only for a pane forgectl owns: the workspace must carry forgectl's ownership marker, the pane must be the root pane its create response named, and `pane get` must place that pane in that workspace. A workspace that is provably absent returns `ErrWorkerGone`; any other failure returns `ErrScreenUnreadable`, which is never a verdict about the worker.

## Briefs, waits and reports

A worker's first brief goes in at launch. `surface launch --brief` appends it to the harness argv after `--`, and the trampoline socket carries that argv to the pane, so the brief is never typed into a running TUI. The brief then stays in the harness's process arguments for the whole session, where `ps -ww` can read it, so a launch brief must not hold a secret. Every harness treats what follows `--` as the prompt: Claude Code 2.1.289 answered `-- mcp` as a prompt rather than running the `mcp` subcommand, and Codex 0.160.0 and Pi 1.0.4 took `-- --help` as one. Pi still reads an argument that starts with `@` as a file to attach, after `--` too (`pi -- '@README.md say OK'` exits `File not found`), so a pi launch refuses a brief that starts with `@`.

`surface brief` types the follow-ups. It writes through `TypeText` (`herdr.send-text`) and `PressEnter` (`herdr.send-keys`). Each call re-runs the ownership check `WorkerScreen` uses, so forgectl types only into the root pane of a workspace it owns. Three herdr and Claude Code facts shape it, measured on herdr 0.9.1 and Claude Code 2.1.289:

- `pane send-text` does not honour `--`; it types the `--`. A text starting with `-` types correctly without one. The sensitive runner still refuses such an operand, so `CheckBrief` refuses a typed brief that starts with `-`.
- Claude Code collapses typed text between 700 and 900 characters into `[Pasted text #N]`, which the read-back cannot compare, so a typed brief is capped at 600 characters with its report instruction.
- herdr reported `working` within 0.4 s of Enter, and `done` when the turn ended.

Every brief carries a random 12-character marker, recorded in the ledger row before the brief is sent. The brief spells the REPORT line out in words, so its own echo never matches `REPORT <marker>:`. `worker.FindReport` also takes only report lines below the last line that names the marker. A report is still the worker's claim, and the coordinator checks it against git.

Every launch brief (`surface launch --brief` and the drain's launches alike) also carries forgectl's worker rule, as its own paragraph between the task and the report instruction: never post a `cadence-review` marker, never approve a pull request, and never merge one, with `gh` or any other way; the operator, or forgectl under its merge policy (see [Merging](#merging)), merges. It names the marker without the colon the policy's marker scan looks for, so a worker that echoes it posts nothing the policy reads as a marker. Intake's brief template carries the same rule. A typed brief (`surface brief`) does not repeat it: it goes to a worker that got it at launch, and must fit the 600-character cap. Workers run on the operator's GitHub identity, so the rule asks; it cannot stop one (ADR-0011, 2026-10-09 amendment).

`surface wait` does not compare screen text for stability, because a harness's status line and any mod drawing above the prompt change every second. It needs the ready verdict to hold for `--settle`, plus one of: a `working` status seen during the wait, the report on screen, or `--quiet` at the prompt.

## What a claude worker loads

A claude worker is a full harness (ADR-0010, 2026-10-08 amendment): it loads what an ordinary session started by the operator loads. That is the operator's user settings and their allow rules, plugins, skills and hooks; MCP servers, plugin-provided ones included (herdr-bridge can drive any herdr pane); Claude in Chrome; `CLAUDE.md` and rules; project auto-memory; and the branch's own `.claude/settings.json` and `.mcp.json`. Nothing is denied: a worker can message other sessions with `SendMessage`. forgectl adds only the following:

- **No `--ide`:** the worker does not ask to connect to the operator's editor.
- **An environment allowlist:** a worker inherits only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `COLORTERM`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, `CLAUDE_CONFIG_DIR`, the CA and config-home paths (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `CODEX_HOME`, `XDG_CONFIG_HOME`) and `SSH_AUTH_SOCK`, plus herdr's pane ids. With `--profile <name>`, `CLAUDE_CONFIG_DIR` is set to that [`[surface.profiles]`](configuration.md#worker-profiles) entry's `config_dir`, over the inherited value and the launch profile's `env`; no other variable is added. `SSH_AUTH_SOCK` is a deliberate grant: the remotes push over SSH, so it stays while workers run as the operator (ADR-0010, 2026-10-06 amendment; forgectl#1134 lists what would replace it). When the launcher is a Claude Code session, its own handles (the cross-session messaging socket and token, the herdr and cmux sockets) stay out of the worker's environment, so a nested `claude` behaves as a fresh session. The operator's user settings `env` block applies again, because user settings load. This is about a clean environment, not containment: a worker has `SendMessage` and herdr-bridge directly.
- **`--settings`:** sets `useAutoModeDuringPlan: false` (forgectl#1060), so a `plan` worker's shell commands prompt rather than going to the classifier.
- **Model:** the matched launch profile's, unless `--model <name>` replaces it for this worker; effort is derived again from the new model, as a `--harness` override does. Only the `sonnet`, `opus` and `fable` aliases map to an effort, so a full model id (`claude-opus-5-5`) or another alias (`haiku`) leaves effort empty and Claude Code's own setting applies. The value is a plain token (letters, digits, `.`, `-`, `_`, `[`, `]`, at most 64 characters, not starting with `-`), so it cannot become a flag.
- **Permission mode:** `[launch.worker] permission_mode`, `acceptEdits` by default; `auto` is allowed (ADR-0010, 2026-10-07), and sends the tool calls the mode does not approve on its own (reads and in-worktree edits are approved) to Claude Code's classifier instead of the operator. `dontAsk` and `bypassPermissions` are refused.
- **An allow list, for `acceptEdits` workers:** `--settings` adds `go test`, `go build`, `make`, `git add`, `git commit`, `git push`, `gh pr create` and `gh pr view` (each as `Bash(<command> *)`). The operator's own allow rules load in every mode as well and usually reach further: with `Bash(gh:*)`, a worker runs `gh pr merge` or `gh api` writes without a prompt. Whether a command prompts depends on those rules, not on this list. A prefix rule cannot see where a push goes, so only a repository ruleset refuses a push to `main` (forgectl and cadence require a pull request).

A unit test pins the argv, the settings JSON and the environment allowlist. What a worker loads beyond that is whatever the operator's own configuration loads, and changes when it does.

## Worker harnesses

A worker runs claude, codex, or pi: the harness the matched launch profile names, or `--harness` on `surface launch` and `surface enqueue`. Each is an ordinary session of that harness (ADR-0010, 2026-10-08 amendment); forgectl adds no isolation and no deny rules for any of them. All three take the environment allowlist above, no harness args, and the brief after `--`.

- **claude:** the section above.
- **codex:** `--sandbox` and `--ask-for-approval` from the worker profile, capped at `workspace-write` and `on-request`; `--model` when one is set.
- **pi:** `pi [--model <name>] -- <brief>`, and nothing else. Pi has no permission or sandbox flag, so a pi worker runs with pi's own config and extensions, as a claude worker runs with the operator's settings. The worker floor still refuses harness args, and still clears `allow_danger` and `add_dir`.

`--profile` sets `CLAUDE_CONFIG_DIR`, so it is refused for codex and pi. Only a claude worker gets a `--session-id` and a transcript path.

## Where a worker branch starts

A `--worktree` branch that does not exist yet starts at the head of the repository's GitHub default branch (forgectl#1061), not at the checkout's `HEAD`, which is often stale or on another branch. forgectl reads the branch and its head commit from the GitHub API, fetches that branch from `origin`, checks the fetched commit is the one GitHub named, and passes the hash to `git worktree add`. Only an `origin` URL whose host is `github.com` or `ssh.github.com` counts as GitHub; any other origin, an SSH host alias for GitHub included, starts the branch at the checkout's `HEAD` as before. A failing GitHub call fails the launch rather than falling back. An existing branch is checked out as it is, and needs no GitHub call.

This is a correctness fix, not a security control. Workers in one repository share its `.git` and are mutually trusting (ADR-0010): an earlier worker can change what the next one starts from.

Every `--worktree` launch whose origin is on github.com also reads the repository's canonical `nameWithOwner` and numeric id from GitHub (one `gh api graphql` query, pinned to github.com) before it writes the ledger row, and records them on the row as `github_repo` and `github_repo_id`. The row also records `branch_from`: `new`, `local` or `origin`, the branch selection above. A failed read fails the launch before anything is created. An origin on another host records neither, and the launch goes on; such a row is never eligible for a merge (see [Status and merge policy](#status-and-merge-policy)). The merge policy reads these recorded values, never the checkout's `.git/config`, which a worker can rewrite after it starts.

A drain launch is stricter: its branch `worker/<name>` must not exist yet, as a local branch, as `origin/worker/<name>`, or on GitHub (the same query asks). One that exists fails the row before anything is created (`refused before launch`, no retry), because the merge policy only trusts a head on a branch the drain made new. The error names the way out: delete the old branch locally and on origin (`git -C <repo> branch -D worker/<name>`, then `git -C <repo> push origin --delete worker/<name>`) and `dequeue` and `enqueue` the row again, or enqueue the work under a new name. `surface close` keeps the branch, so a name that was closed needs this before it is enqueued again. `surface launch --worktree` by hand still checks out an existing branch as before, and records where it came from. The identity read is best-effort by hand: when GitHub cannot be read, the launch prints one warning line, records no repository (such a row never passes the merge policy), and goes on. For the drain the same failure pauses claiming (below). These ledger fields are new without a version change, so a drain or `surface` command running an older binary refuses a ledger holding them; restart the drain after upgrading.

## Listing and closing workers

`surface list` probes each ledger row's workspace through `Adapter.Probe`, the same lookup `Close` uses: the server incarnation must match the reference, the listing must be complete, and the workspace must carry forgectl's ownership marker. The incarnation is the session's socket, not the way the session was chosen: no `HERDR_SESSION` and `HERDR_SESSION=default` select one server, so a plain CLI reads and closes the workers the drain launched with the pin. A reference from the default session is refused outright in any other named session, and one from another named session fails the incarnation check. A workspace missing from that listing is `gone`. Any herdr error is `unreadable`, and so is an identity mismatch: after a herdr restart, or when a workspace id now names a workspace without forgectl's marker, nothing proves forgectl's own workspace gone. `--orphans` keeps the rows `close` should act on: a `gone` workspace, or any stage other than `launched` (`failed`, `closed`, or a launch stopped at `pending` or `worktree`). A launch at `pending` or `worktree` for less than ten minutes may still be running, so it is never an orphan, and `close` refuses it.

A claude worker is started with a forgectl-generated `--session-id`, and its row records the transcript path Claude Code writes: `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<slug>/<id>.jsonl`, where `CLAUDE_CONFIG_DIR` is the worker's own (a `--profile` launch's is the profile's `config_dir`), where the slug is the worktree path with every character other than an ASCII letter or digit replaced by `-`. The path comes from the environment the harness was started with. Codex and pi workers have neither field.

`surface close` closes the workspace first, so the harness stops before its worktree is judged. It refuses, touching nothing, when the close comes back unreadable, failed, or an identity mismatch. A row at stage `closed` skips herdr: an earlier close already closed its workspace. It then removes the worktree only when `git status --porcelain --ignored` is empty, HEAD is on a branch, the branch has nothing beyond its upstream (or, with none, beyond the commit the worktree started at), and no stash entry names the branch. The path comes from `git worktree list`, not the ledger, and `git worktree remove` runs without `--force`, so git refuses on its own if a tracked or untracked file changed after the checks. Git does delete ignored files, so an ignored file written after the check is lost; closing the workspace first stops the harness that would write one. The ledger row is removed or marked `closed` only if it is still the row close read, so a launch that reused the name meanwhile is left alone. The branch is never deleted. A kept worktree leaves the row at stage `closed`; a later close retries it.

`surface close --dry-run` previews that decision and changes nothing. It runs the checks that need no write: the launch-in-flight refusal, the ledger stage, and the read-only worktree inspection. herdr is not asked, so a workspace close would close reads `would-close`, and the preview cannot say whether herdr would refuse. It prints `workspace` (`would-close`, `closed-earlier`, `none`, `refused`), `worktree` (`would-remove`, `would-keep`, `gone`, `untouched`), `kept_because`, and `would_forget`; with `--json`, `{name, branch, dry_run, refused, workspace, worktree, kept_because, would_forget, reason, note}`. Text mode prints a `refused=` line too. Where close would refuse, the preview prints the same lines (or the same JSON object) and then exits 1, with the reason as the error, so `close --dry-run && close` stops where close would. The preview and the real close share one decision for the workspace and one for the worktree; only what needs herdr, or a write, differs. The worktree inspection runs `git status` with `--no-optional-locks`, so the preview takes no `index.lock` and rewrites no index. A worktree in the middle of a rebase or bisect can list as a detached HEAD, which blocks removal (`would-keep`).

`surface launch --dry-run` previews a launch: it checks that the backend is on `PATH`, the target resolves, the harness profile builds (and passes the binary policy), and, for `--worktree`, that the name is free in the ledger and the branch and worktree path are usable. It then prints what it would create and creates none of it: no worktree, `.claude` directory, branch, ledger row or surface, and no call to the backend. It never prints the harness path, arguments, environment or brief. A new branch reads as `branch_from=new`; its base commit is read from GitHub when the launch runs, not by the preview. The preview refuses a local branch that another worktree (the main checkout included) has checked out, which git would refuse. It cannot see any other refusal git makes only when `git worktree add` runs, so a clean preview is not a promise. `--json` (which needs `--dry-run`) prints `{dry_run, surface, name, target, harness, worker}`, with `worker` (`{repo, worktree, branch, branch_from, ledger_row, brief, posture}`) only for `--worktree`. `posture` shows the worker posture the launch would use, so an operator can confirm `auto` took effect: each field the harness takes (claude `permission_mode`; codex `sandbox` and `approval_policy`; pi none) maps to `{value, source}`, where `source` is `default` (the built-in worker value), `launch.worker`, or `repo-profile` (a stricter matched project block). The text preview prints `permission_mode=auto` and `permission_mode_source=launch.worker` lines.

## Queue

`surface enqueue --repo <path> --name <slug> --brief <file>` adds a brief to the machine's queue, `$XDG_STATE_HOME/forgectl/surface/queue.json`, for the drain (`surface drain`, below) to launch as a worker. `--harness claude|codex|pi` (default `claude`) is stored on the row, and the drain launches the row with it; a row written before the field existed runs claude. The file is written like a ledger: through the pinned surface directory, opened without following a symlink, 0600 in a 0700 directory, under an flock on `queue.lock`, and replaced by an atomic rename. A file with an unknown version, field or state is refused, not rewritten. `name` is unique across the whole queue. The brief file is read once and stored as text: at most 64 KiB, checked as a launch brief, and it may not start with `@`. `--profile <name>` and `--model <name>` choose the worker's [`[surface.profiles]`](configuration.md#worker-profiles) entry and model, as on `surface launch`: the profile for claude only, the model for every harness (its `--model`); the row stores the profile's name (`main` as none), never its path, and an unknown name is refused at enqueue. Enqueueing a name again with the same brief, harness, profile and model changes nothing and prints the row's state; a different brief or repository is refused, naming both brief hashes, and so is another harness, profile or model. The document stays under 768 KiB, and an enqueue past that is refused before anything is written. A row in a terminal state (`reported`, `failed`, `closed`, `expired`) drops its brief text and keeps `brief_sha256`. `surface dequeue <name> [--json]` removes a row unless its worker may be live (`claimed`, `launched`, `needs-you`), which needs `surface close` first; after a dequeue the name can be enqueued again, which is how a `failed` row is retried. `surface queue [--json]` lists each row's state and how long it has been in it, and never prints brief text. The drain claims a row by moving it from `queued` to `claimed` under the queue lock and writing its `launch_id`, so of two claimers exactly one wins. A `reported` row can also carry `pr_closed_at` and `cost_usd`, which the drain's closers write (see [Drain](#drain)); `surface queue --json` shows both.

## Intake

`surface intake gh --repo <path>` turns open GitHub issues that carry an eligible label into queue rows, so the drain works them. The label is the request. Removing it stops later intake runs from taking the issue; a row already queued stays, and launches, until `forgectl surface dequeue <name>` removes it. The operator runs intake by hand at a terminal and confirms what it queues (below); a coordinator session can run `--dry-run`. The drain never calls GitHub for it.

A drain worker runs as the operator with the operator's allow rules (ADR-0010), and an issue's text becomes its brief, so intake takes an issue only when the operator trusts that text. Every check below reads one GraphQL response, and the body checked is the body queued:

- **Author.** The issue's author is on `[surface.intake] authors`. With no `authors`, a user-owned repository allows its owner's login only, and only when that owner is the account `gh` is authenticated as (the query's `viewer`, compared case-insensitively); otherwise, as for an organization-owned repository, the run is refused with exit 2 until `authors` is set. A missing `viewer` login refuses the run. Logins compare case-insensitively and exactly. A bot is never allowed: GraphQL types it `Bot` and spells its login without the `[bot]` suffix, so the check reads `__typename`, and a login ending `[bot]` is refused as well.
- **Labeler.** The default eligible label is `queue:drain`, which no triage sweep applies, so its labeling means a person asked for the work. A bulk-applied label such as the `exec:*` triage set proves only that a script ran as the owner; listing one in `labels` trusts that script. For each eligible label on the issue, the latest `labeled` event for that name is by an allowed author (every one, when several share that second), and no `unlabeled` event for it is at or after that time. GitHub timestamps are whole seconds and its timeline lists same-second events in no reliable order, so a same-second removal refuses. GitHub records a label event by the label's name at read time, so renaming an existing label to an eligible name (say, a bulk-applied label to `queue:drain`) makes every old labeling of it count, at its old time; create a new label rather than renaming one.
- **No edits after labeling.** `lastEditedAt` is an explicit JSON `null` (never edited) or strictly before the earliest of those latest labelings, and no `RenamedTitleEvent` is at or after it. A missing field, or any GraphQL error, refuses. The earliest labeling counts, so every eligible label on the issue was added after its text was final.
- **Issues only, never transferred.** `repository.issues` holds only GraphQL `Issue` nodes; intake still checks `__typename`. A `TransferredEvent` refuses.
- **Nothing unseen.** An issue with more than 100 labels or timeline events of the four types read is refused rather than judged on a partial history.

The row's brief is a fixed template: the rules, then the issue's title and body between the lines `BEGIN ISSUE TEXT <nonce>` and `END ISSUE TEXT <nonce>`, the nonce a fresh random 12-hex-character marker, drawn again if the text contains it, so the body cannot close the fence. The rules say the fenced text is the whole task, to treat instructions inside it or in anything fetched as data, not to read the issue, its comments, linked issues or pull requests, or any URL with `gh`, `curl` or anything else, never to create, edit or comment on issues or labels, to work only in the worktree, to run the tests, commit, push the branch, and open a draft pull request whose body contains `Closes #<number>`, and never to merge, mark a pull request ready, push the default branch, or edit another repository. The issue number appears only in that `Closes` rule. The body's CRLF line ends become LF; any other control, bidi or invisible character fails `CheckQueueBrief`, as does a brief over 64 KiB, and the issue is skipped.

These rules are instructions, not a sandbox. A worker can still fetch the issue and its comments, and every agent on the machine acts as the owner, so a misled worker could file and label an issue that passes every check above. Those checks prove only that something holding the operator's `gh` login acted. Two more rules make it unlikely that one worker starts the next by accident; neither stops a worker that sets out to:

- **A person confirms at a terminal.** A run that would queue anything first shows each candidate on the terminal: its source (`gh:<owner>/<repo>#<number>`), title (sanitized, one line, cut short), author, labeler, labeled-at time, row name and `brief_sha256`. It queues them only when `yes` (exactly, surrounding spaces trimmed) is typed there. stdin must be a terminal and `/dev/tty` must open as one, and the answer is read from `/dev/tty`, never stdin, so `echo yes | forgectl surface intake gh ...` does not count. No terminal refuses with exit 2 ("intake needs a person at a terminal to confirm; run it from a plain terminal, or use --dry-run"); end of input or any other answer queues nothing and exits 1. There is no flag that skips the question. A run with nothing to queue asks nothing, and `--dry-run` never asks. With `--json` the list and the question still go to the terminal, and stdout carries only the JSON result. It shows that a terminal answered, not that a person did: a process can give itself a terminal (`script`, `expect`, a pty library, `tmux send-keys`, or herdr-bridge typing into a pane) and type `yes`. It is a stopgap against accidents while workers share the operator's `gh` identity (ADR-0010, 2026-10-09 amendment).
- **Not inside a drain worker.** Every worker launch (the drain's and `surface launch --worktree`'s) sets `FORGECTL_DRAIN_WORKER=1` in the worker's environment, after the allowlist and the profile's env, so the harness and its shells inherit it. Intake, `surface enqueue` and `surface launch` refuse with exit 2 when it is set to any non-empty value; intake does so before it reads GitHub. A worker runs as the operator and can unset it, so this is a courtesy refusal against accidents.

`max_per_run` and the label-as-request model limit how far one mistake spreads.

- **Repository.** `--repo` is a project name or path, as on `surface enqueue`; intake reads `owner/repo` from its `origin` remote, which must be on `github.com` (or `ssh.github.com`), and refuses any other host. The query runs as `gh api graphql --hostname github.com` through the host-pinned runner. If GitHub names a different owner than origin (a rename or transfer it followed), intake refuses.
- **Rows.** Each row is named `gh<number>-<repo name>`, the name lowercased with other characters mapped to `-` and cut so the whole name fits 48 characters; the number is always kept. It records `source` (`gh:<owner>/<repo>#<number>`), `author` (the issue's author), `labeler` (the login that applied the admitting label) and `labeled_at` (when, RFC 3339), all shown by `surface queue --json`. The admitting labeling is the earliest of the latest labelings of the eligible labels on the issue, the one the edit checks compare against. `--harness`, `--model` and `--profile` apply to every row the run adds. These four fields are new in the queue file without a version change, so a drain running an older binary refuses a queue file holding an intake row and must be restarted after the upgrade.
- **Dedupe.** An existing row of the same name, in any state, skips the issue naming its state (`failed` adds "dequeue it to retry"); one held by another repository is skipped naming that repository. `dequeue` makes the issue eligible again on the next run if it still carries the label.
- **Per issue.** Every refusal or skip is reported with the issue number and reason, and the run goes on. Nothing is queued until the confirmation, so a GitHub read failure stops the run with exit 1 and queues nothing. A full queue stops the run with exit 1 and keeps the rows queued before it. `[surface.intake] max_per_run` (default 5) caps the candidates one run gathers; at most 20 pages of 25 issues are read per run.
- **Preview.** `--dry-run` reads GitHub and the queue, asks nothing and writes nothing. `--json` prints `{dry_run, repo, github, authors, labels, enqueued: [{number, name, source, author, labeler, labeled_at, brief_sha256}], skipped: [{number, name, source, author, labeler, labeled_at, reason}], stopped}` on stdout; with `--dry-run`, `enqueued` is what would be queued. A declined confirmation lists every candidate under `skipped` with the reason `not confirmed at a terminal`.
- **Config.** `[surface.intake]`: `authors` (GitHub logins), `labels` (default `["queue:drain"]`; `--label` narrows to one of them), `max_per_run` (1 to 50, default 5). A bad value, or an unknown key such as a misspelled `lables`, makes the config file invalid at load, and intake refuses it again; it never falls back to a default.

Exit 0: the run finished, whatever it skipped. Exit 1: the answer was not `yes`, GitHub could not be read (nothing queued), or the queue filled (what came before stays queued). Exit 2: a usage or setup error, including no terminal to confirm at and a run inside a drain worker.

## Drain

`surface drain start` starts a detached process that launches the queue's rows as herdr workers, each with its row's harness, and watches them. It is the one unattended launcher: it never types into a pane and never answers a prompt; a worker stopped at a prompt waits for the operator in its own pane.

- **Start and stop.** `start` resolves the herdr session the way `surface launch` does and starts `forgectl surface _drain` with `Setsid`, `/dev/null` stdin, this command's environment, and `HERDR_SESSION` pinned to that session; the child refuses to start if herdr or the session resolve differently (checked at startup only; later ticks resolve `herdr` from the same inherited `PATH`). Before it starts the child, `start` creates and removes one private run directory where every launch makes its own (`os.TempDir()`, from `TMPDIR`), and exits 2 naming `TMPDIR` when it cannot: an unset `TMPDIR` on macOS is `/tmp`, a symlink. `start` waits up to 5 s for `drain.json` to show `running` or `paused`, otherwise exits 1 printing the last events line. A second `start` while a drain holds `drain.lock` (flock, `LOCK_EX|LOCK_NB`) exits 1 naming the holder's pid and start time. `stop` sends `SIGTERM` only when `drain.json` records a non-zero process start time equal to the live process's (`internal/procstart`); the drain finishes its current step (a launch in progress completes) and exits, writing `stopped`. A crash releases the flock, and the next `start` takes over.
- **Files.** `drain.lock`, `drain.json` (status, replaced atomically each tick) and `drain-events.jsonl` (appended; renamed to `.1` when it would pass 1 MiB, replacing the previous `.1`) sit beside `queue.json` and go through the same pinned directory and verified open: 0600 files in a 0700 directory, no symlink followed.
- **Config.** `[surface.drain]`: `interval` (default `"15s"`, at least `5s`), `cap` (default 3, at most 10), `per_repo` (default 1), `notify` (default `true`), `idle_minutes` (default 10). The drain reloads the config file every tick. A file that does not load, or an out-of-range value, pauses claiming with the reason in `drain status` and the events; it never falls back to a default. Watching continues with the last valid values.
- **Slots.** A row in `claimed` holds a slot, and so does any row whose own ledger row (same `launch_id`) is at `pending`, `worktree` or `launched`, whatever the queue says: a `failed` row with a live worker holds its repo's slot until `surface close`. A `reported` row frees its slot even while its worker runs (a worker can print its report early; P4 checks reports against git).
- **Each tick**, in order: claimed rows left by a launch that is no longer running are settled from their ledger row (none or another `launch_id`, or created nothing → `queued` with no attempt; `pending` or `worktree` → `failed` naming the worktree; `launched`, `failed`, `closed` → the same). Each `launched` or `needs-you` row gets one screen read: its REPORT line → `reported`; a blocking screen → `needs-you`, notified once; any other verdict while `needs-you` for a blocking screen → `launched`; at the prompt with no report for `idle_minutes` → `needs-you` (`idle without report`), which clears once the worker is working again; ledger row `closed` or removed → `closed`; ledger row `failed` or the workspace gone → `failed` (a gone workspace's row still holds its slot, and its last error says to run `surface close <name>`); an unreadable pane or ledger leaves the row as is and records one event. A `reported` or `failed` row whose own ledger row is then closed or removed by `surface close` → `closed`; a row failed with nothing of its launch left (a refused row, a taken name, three empty attempts) drops its `launch_id`, so this never mistakes another launch for its close. Each `reported` row then goes through the closers (below), and with `[surface.merge] mode = "auto"` one of them may go through the autopilot (below). Rows `queued` for more than 7 days → `expired`. Then, unless paused, the oldest `queued` rows are claimed one at a time (`launch_id` and the herdr session written under the queue lock) and launched outside it through the in-process worker launch, with the row's harness, branch `worker/<name>`, after re-checking the row's repo (clean, absolute, still its own top), brief (`CheckQueueBrief`), brief hash and harness (claude, codex or pi; a profile only with claude). Once each UTC day the tick ends with `surface prune` (below) at the default cutoff.
- **Profile and model.** A row's profile name is resolved from the config file the tick loaded, at launch, and its `config_dir` becomes the worker's `CLAUDE_CONFIG_DIR`; the row's model replaces the launch profile's. A name the config does not define is a launch-config failure before anything is created: the row goes back to `queued` with no attempt counted and claiming pauses until the next `drain start`. A row whose stored profile name or model is not the right shape is refused before launch, like a bad brief.
- **Session cap (claude-slots).** `_drain` resolves `claude-slots` on `PATH` once at startup and records it in `drain.json` as `claude_slots_path`. Before each claude launch (after the claim and the row's re-check), it runs `claude-slots check <N>`, capped at 5 s, with the drain's environment. N is 1 plus the launches this tick has already made, since a session launched moments ago may not be registered yet: with one slot free and three rows planned, only the first launches. A check cut short because the drain is stopping launches nothing and records no event. Exit 0 launches. Exit 1 puts the row back to `queued` with no attempt counted and its `launch_id` dropped, sets `last_error` to the tool's first output line, and claims nothing more that tick; one `slots-held` event names the reason when the drain enters that condition, not one per tick (a tick with nothing to claim ends the condition, so a later hold records a new event), and the claim and requeue write no `state` events. Any other exit code, a run that fails to start, or a timeout launches as if the tool were missing, with one `error` event per condition. A codex or pi row is not a claude session and launches without the check. When `claude-slots` is not on `PATH` at startup, the drain records one `note` event ("claude-slots not found; launching without the session cap") and launches as before. A held claude row does not block codex or pi rows in the same tick, which are not claude sessions; later claude rows that tick are skipped. The tick plans rows oldest first up to `cap`, so with `cap = 1` a held claude row still holds the only planned slot. Every launch in a tick counts toward the slots the next claude check asks for, which errs strict.
- **Launch failures.** A failure that created nothing goes back to `queued` with one more attempt, and to `failed` at the third. A failure after anything was created (worktree, workspace, recovery tag) is `failed` at once, naming the error, worktree and ledger stage; so is a name the ledger already holds. The way back is `surface close`, then `dequeue` and `enqueue`; `close` keeps the branch `worker/<name>`, so delete it locally and on origin first, or enqueue under a new name. A GitHub auth failure, GitHub unreadable for the repository identity a launch records, herdr unreachable, or a launch configuration that cannot build a worker (the worker posture, the harness profile, a harness binary found only on `$PATH`), or a private run directory the environment cannot provide (a `TMPDIR` that is a symlink, too long, or shared without the sticky bit), pauses claiming. The row goes back to `queued` with no attempt counted when the failure created nothing, and is `failed` naming its worktree otherwise. A herdr pause is re-checked each tick (the drain asks herdr's readiness before claiming). A GitHub-read pause (`github`) is re-checked each tick too: when it is the only pause held, one row is claimed, its identity read is the check, and a successful launch clears the pause. An auth or launch-config pause lasts until the next `drain start`. The drain never passes `--allow-path-binary`: name each harness's binary in `[launch.defaults]` (`binary_path`, `codex_binary_path`, `pi_binary_path`) or its `FORGECTL_*_BIN` variable.
- **Status and events.** `drain status [--json]` prints `running`, `paused` (with the reason), `stopped`, or `stale` (last tick older than 3 intervals), the pid, start time and herdr session, counts per state, the rows in `needs-you` or `failed` with their last error, and `held_slots` with the names of the rows `holding` them, so a queue held back by failed rows whose workers are still live is explainable. `drain events [--since <seq>] [--json]` prints `{v, ts, seq, kind, name, repo, state, attempt, error}` lines, kinds `start`, `stop`, `state`, `pause`, `resume`, `unreadable`, `error`, `slots-held`, `note`, `merged`, `merge-refused`; `seq` counts from 1 in each drain process, so `--since` reads only the latest run.
- **Needs-you notifications.** When a row enters `needs-you` and `[surface.drain] notify` is on, the drain does two things, once per entry. On macOS it posts one notification, title `forgectl: <name> needs you`, body the reason (`blocked: <screen>` or `idle without report`), through `osascript` with both as arguments, never as script text. It also puts the worker's own pane in herdr's needs-you state (`pane report-agent --source forgectl-drain --state blocked`, message `forgectl: <name> needs you — <reason>`). That pane comes from the worker's ledger ref, on the drain's pinned herdr session, and only after the same checks a screen read makes: the workspace carries forgectl's marker, the pane is the root pane the create named, and herdr places it in that workspace. The drain's own `HERDR_PANE_ID` is never used. A pane that fails a check is left alone and the macOS notification still goes out. When the row leaves `needs-you`, the drain releases the `forgectl-drain` state on the pane, whatever `notify` says, so turning it off never strands a marked pane; a closed workspace has nothing to release. A failed notification or release never fails the tick: it is one `error` event per entry or exit, not one per tick. The one `notify` switch covers both halves; the desk's `notify_macos` and `notify_herdr` do not apply to the drain.
- **Closers.** A `reported` row whose own ledger row is readable and not yet closed has its PR read at most once every 5 minutes, at most 4 rows a tick, oldest read first. The read is the discovery query `surface status` uses, with the same filter (the head branch `worker/<name>` on the repository the ledger row recorded, not a fork, by the operator, created at or after the ledger row's `started_at`, at most one open PR), and nothing else. A PR from an earlier launch under the same name is never this launch's, so a reused name's merged PR cannot close a new worker. What it finds:
  - **Merged:** the session is priced with `cadence-hooks metrics price` when `cadence-hooks` is on `PATH` and the row has a transcript; `cost_usd` is set only when every model was priced. Then the drain runs the close `surface close` runs (the same code). When close refuses (herdr unreadable, an identity mismatch), the row stays `reported` and one `error` event names why; it is tried again at the next read. When the close worked but its ledger row could not be marked closed or removed, the row also stays `reported`, with that note as its last error and one `error` event, and the next read closes again (herdr answers already gone) and retries the ledger write. Otherwise the row goes to `closed`, its last error naming the PR, and a kept worktree and any note from the close (such as a recovery tag to check by hand) are named there too, the note also as one `note` event.
  - **Closed unmerged:** the first sighting records `pr_closed_at` and a `note` event; 24 hours after it the worker is closed the same way, unpriced. A PR seen open again clears `pr_closed_at` (a `note` event), and a later close starts the 24 hours again.
  - **No PR:** the row stays `reported` (`surface status` shows "no PR"). Close it by hand when the worker made no PR.
  - **A failed read** changes nothing and pauses nothing. A network failure, server error or rate limit is one `unreadable` event, anything else (a GitHub refusal, two open PRs, a recorded repository whose id changed, a PR whose `createdAt` cannot be read) one `error` event, each once until the read works again.
  - A row whose ledger row records no GitHub repository is never read: one `note` event says so, and it stays `reported` until `surface close`.
  The read times and the once-per-condition events live in the drain process only; a restart reads every reported row again. `pr_closed_at` and `cost_usd` are new queue fields, and `closed_at` a new ledger field, all without a version change. An older binary therefore refuses the whole queue file once a row carries one, and refuses the whole ledger file once a row carries `closed_at`, which stops its `surface launch`, `close` and `list` for that repository as well as the drain. Upgrade every forgectl on the machine and restart the drain together.

- **Autopilot.** Only while `[surface.merge]` resolves to `mode = "auto"`, read again from the config file every tick, so setting any other mode (or breaking the file) stops the next attempt with no restart. After the closers, the drain reads the queue and ledgers again (the closers may have just closed a row) and makes at most one merge attempt that tick, through the same merge path `surface merge` uses (see [Merging](#merging)), as the drain: `Merged-By: forgectl-drain`, actor `drain` in the audit. A candidate is a `reported` row whose own ledger row is readable and still `launched`, with the queue row's `launch_id`, `branch_from` `new` and a recorded GitHub repository; the merge policy checks all of this again. The row tried longest ago goes first, and each row is tried at most every 5 minutes, since each attempt reads the PR in full. A merge is one `merged` event naming the PR, head and merge commit, and the closers read that row at the next tick and close the worker; the autopilot does not try a row it merged again (same name and `launch_id`) while it stays `reported`. A refusal, or a merge that failed, is unconfirmed, was made by something else or is not known, is one `merge-refused` event per row, head, result and reason set; GitHub unreadable is one `unreadable` event until a read works. Refusals are audited too, limited as below; a refusal whose audit line could not be written (a full file, say) is also one `error` event, while a refusal the audit skips as a repeat raises none. The attempt times and the once-per-condition events live in the drain process only. An attempt is capped at 3 minutes and usually takes seconds; a slow one holds the tick, so `drain status` can read `stale` while it runs.

## Prune

`surface prune [--older-than <duration>] [--dry-run] [--json]` removes old rows from the queue and from every ledger in the state directory. `--older-than` takes `30d`, `720h` and the like; the default is `30d`, and anything under `1h` is refused (exit 2).

- **Queue rows** in state `closed`, `failed`, `expired` or `reported` whose `state_at` is older than the cutoff go, unless the row's own ledger row (same name and `launch_id`) still has a herdr workspace that herdr says is live, or cannot rule out; that row stays, naming `surface close`. A `reported` row normally leaves through the closers or `surface close`; one neither settled for the whole cutoff (no PR and nobody closed it) goes the same way once its workspace is not live, so it cannot hold its place forever. When a ledger file cannot be read at all (it does not parse, or is not named for its own repo and session), every launched queue row whose ledger is not among the readable ones stays, naming that file, since its ledger row may be in it.
- **Ledger rows** at stage `closed` (a close that kept the worktree) go once their `closed_at`, written by the close that first kept the worktree, is older than the cutoff and the worktree they record no longer exists; while it exists, or cannot be checked, the row stays and says why, since it is the only record of that worktree. A row closed before `closed_at` existed has none: it goes only when its `started_at` is older than the cutoff and its recorded worktree path no longer exists, and stays, saying why, while the path exists, cannot be checked, or was never recorded. When herdr cannot be read (no herdr session, or its server is down), no ledger row is removed, and the output says so.
- **Status cache entries** (`status-cache-<head>.json`, written by `surface status`) last written before the cutoff go. Rows do not record the head an entry serves, so the entry's age stands in for "with its row".
- **Each removal** is conditional: a row that changed since prune read it stays, with that reason.
- **`--dry-run`** reads everything and writes nothing. `--json` prints `{dry_run, older_than, cutoff, removed, kept, usage, notes}`, each row `{kind, name, repo, session, state, at, cost_usd, reason}` with `kind` `queue`, `ledger` or `status-cache` (named by its head); with `--dry-run`, `removed` is what would go.

Exit 0: pruned or previewed. Exit 1: the state could not be read or written (the queue, the drain files, the status cache or the ledger directory). Exit 2: a usage error only, such as `--older-than` under `1h`.

The drain runs prune with the default cutoff once each UTC day, at the end of the first tick of the day. It records the day in `drain-prune-day` beside `drain.json` before it runs, so neither a restart nor a failed prune runs it again that day; a `drain-prune-day` that cannot be read is one `error` event, and the prune runs and rewrites it with today. The daily prune is capped at 30 s, so it cannot hold a tick long enough for `drain status` to call the drain stale at the default interval, and herdr is read once per prune (one readiness check and one workspace listing), not once per row. A failure is one `error` event and never stops the drain; each removed row is a `state` event with state `pruned`.

### usage-daily.jsonl

Before prune removes a queue row with a `cost_usd`, it appends one JSON line per removed row to `usage-daily.jsonl` in the state directory: `{"day":"2026-10-09","name":"fix-login","launch_id":"…","costUsd":1.75}`, `day` being the UTC day of the row's `state_at`. The lines are written under the queue lock before the rows go, and when they cannot be written no row is removed, so a cost is never lost. A prune that fails after the lines are written leaves the rows in place, and the next run writes their lines again, so to read the file sum the unique `(name, launch_id)` lines per day. The file is append-only and never pruned or rotated: it is the long-term cost record, rotated by hand.

## Status and merge policy

`surface status <name> [--repo <path>] [--json]` shows a worker's pull request and what the merge policy decides about it (ADR-0011, 2026-10-09 amendment). It reads GitHub and changes nothing there. The drain's closers (see [Drain](#drain)) find the PR the same way. `surface merge` and the drain's autopilot merge through the same reads and verdict (see [Merging](#merging)).

- **Which PR.** status looks for PRs whose head branch is `worker/<name>` on the repository the ledger row recorded at launch (`github_repo` and `github_repo_id`, above), never the checkout's origin. Before any ordering it drops every PR that is cross-repository, whose head repository id is not the repository's own, whose author id is not that of the account `gh` is authenticated as, or that was created before the ledger row's `started_at` (an earlier launch under the same name). A PR left after the other checks whose `createdAt` is missing or does not parse, or a ledger row with no `started_at`, fails the read (exit 1) rather than guess. More than one open PR left is refused; one open PR is the one; with none open, the most recent closed or merged PR is shown. A PR number from a worker's report is never used. A row with no recorded repository (launched before the record existed, or an origin not on github.com) exits 2.
- **One head.** The PR query names the head commit. Every later read names it, or the base, explicitly: the check runs come from `commit(oid: <head>)`, and that query reads the PR's head and base again and fails if either moved, so a push during the read exits 1 and asks for another run. Files come from `compare/<base>...<head>` and must number the PR's `changedFiles` (the compare API lists at most 300); modes come from one git tree listing per changed directory at the merge base and at the head (at most 100 listings). GitHub connections are read in one page; a response that says another page remains is refused. Every call is `gh api --hostname github.com` through the host-pinned runner.
- **Cache.** Only the file list and modes are cached, one `status-cache-<head>.json` per head in the surface state directory, and an entry is used only when it was written against the same base. Any session on your account can write that directory, so status never shows `pass` on cached data: when a read that used the cache would pass, it reads everything again without it. `surface merge` and the drain never read it. `surface prune` removes entries last written before its cutoff.
- **Cost.** When the row records a transcript and `cadence-hooks` resolves on `PATH`, status runs `cadence-hooks metrics price --transcript <path> --json` with a 15 s cap. Any failure leaves `usage` null; it never fails status. When the transcript used a model with no price, `priced` is `false` and `unpricedModels` names them: `costUsd` then covers the priced models only and is not the session's cost. Model names have control, bidi and invisible characters stripped.
- **Output.** A few lines of text, or with `--json`: `{name, repo, pr:{number,url,state,isDraft,headSha,baseRef,mergeable,mergeStateStatus,changedFiles}, checks:[{name,workflow,event,conclusion}], reviews:[{reviewer,sha,crit,imp,url}], policy:{mode,verdict,reasons[]}, usage:{costUsd,byModel,priced,unpricedModels}|null}`. `pr` is null when the branch has no PR, and `reviews` lists the cadence-review markers posted by `marker_author_id`, the ones the verdict counts (none, with a note, when it is not set). Exit 0 when status was read, whatever the verdict (a recorded base GitHub does not have is a refusal reason, not a failed read); 1 when GitHub could not be read; 2 on a usage or setup error.

### The policy

`[surface.merge]` in the config file sets it (see [configuration.md](configuration.md)). It is re-read on every call, and resolves to `off` on a missing table, any decode or shape error, an unknown key, a `machine` that is not this machine's, or a config file that is a symlink, not a regular file, not owned by you, not mode `0600`, or has more than one hard link. Two `workflow`, `required_checks` or `paths` keys that differ only in case are refused. `machine` is the first 12 hex characters of `sha256(<host name> + "forgectl-merge-v1")`, with the host name the operating system reports (on macOS that is usually `<name>.local`); `forgectl surface merge-machine` prints the value to paste.

```toml
[surface.merge]
mode = "manual"                    # off | manual | auto
machine = "f8e7a19c22c0"           # forgectl surface merge-machine
approvers = ["cadence-review"]     # the one approver implemented
marker_author_id = 4084915         # the operator's numeric GitHub user id
required_reviewers = ["cadence-forge-security-reviewer", "polish"]
method = "squash"
repos = ["cameronsjo/forgectl"]
[surface.merge.workflow]
"cameronsjo/forgectl" = ".github/workflows/ci.yml"
[surface.merge.required_checks]
"cameronsjo/forgectl" = ["build-test", "lint", "macos-test"]
[surface.merge.paths]
"cameronsjo/forgectl" = ["internal/tasks/**", "docs/**"]
```

A glob is matched segment by segment against the path's exact bytes, case-sensitively: `*` is any run of characters within one segment, and `**` is any number of whole segments, allowed only as a whole segment after at least one literal one. A bare `*` or `**`, `**` first or inside a segment, `?`, `[`, `{`, and anything a path may not hold (below) refuse at load.

The verdict is `pass` only when all of these hold at one head; otherwise `refuse`, with one sentence per failing check naming what was expected and what was seen, or `off` when the mode is off (the drain needs `auto`):

1. **Repository.** The recorded repository's id is still its id on GitHub and its name is unchanged; it is on `repos` (compared case-insensitively) with a `workflow`, `required_checks` and `paths` entry; and it is none of the built-in refusals: the repositories a `workbench` marketplace entry installs from, `cameronsjo/cadence`, `cameronsjo/cadence-lab`, `cameronsjo/workbench` and the dotfiles repositories, matched by name and by id, whatever the config says.
2. **Row.** The ledger row's `launch_id` is non-empty and equals its queue row's (a launch by hand never passes), its branch is `worker/<name>` and `branch_from` is `new`, the ledger stage is `launched` and the queue state `launched` or `reported`, the PR's head branch is the row's, and the row's base is an ancestor of the PR's base and of its head (`compare` says `ahead` or `identical`).
3. **PR.** Open, not a draft, targeting the default branch, `mergeable` `MERGEABLE`, `mergeStateStatus` `CLEAN` or `HAS_HOOKS`, not cross-repository, by the operator.
4. **Checks.** Only runs whose check suite GitHub ties to this PR count: the suite's head branch is the PR's, and its `matchingPullRequests` include the PR. A run at the same commit for another PR is ignored. For each required name, every such run at the head from the GitHub Actions app, from the pinned workflow file, on a `pull_request` event, must be `COMPLETED`/`SUCCESS`, and there must be at least one: a run still queued or in progress refuses ("still running"), and so does a failed run beside a later success. A run of that name with no workflow run behind it, from another app, or from another workflow file refuses. A run from the pinned workflow on any other event (`push`, `workflow_dispatch`, `schedule`) never counts, and refuses, naming its event, unless it is `COMPLETED`/`SUCCESS`. A commit status (CodeRabbit's "Review rate limited" `success`, say) never counts.
5. **Paths.** The file list is complete, and every path (both names of a rename) matches the repository's globs. Refused whatever the config says: a path with an empty, `.` or `..` segment, a leading `/`, a backslash, a control byte, a non-ASCII byte or invalid UTF-8; a status other than added, modified, removed or renamed; a mode other than `100644` on either side, or a mode change; a removed `*_test.go` (a rename away from one counts); `go.mod`, `go.sum`, `go.work` or `go.work.sum` anywhere; `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain`, `rust-toolchain.toml`, `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `yarn.lock`, `bun.lockb`, `bun.lock`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `requirements*.txt`, `pyproject.toml`, `uv.lock`, `poetry.lock`, `Pipfile`, `Pipfile.lock`, `Gemfile`, `Gemfile.lock`, `.tool-versions`, `.mise.toml`, `mise.toml`, `flake.nix`, `flake.lock`, `Dockerfile` or `Makefile` anywhere, and any path under a `.cargo` directory at any depth; every top-level file (any path with no `/`: `main.go`, `go.mod`, `.golangci.yml`, `.goreleaser.yaml`, the release-please files, `AGENTS.md`, `CLAUDE.md`, `.coderabbit.yaml`, and any root configuration added later); `.github/**`, `.claude/**`, `scripts/**`, `helper/**`, `internal/cli/**`, `internal/selfupdate/**` and `internal/bless/**`; and every package compiled into the merge path (`internal/surface/**`, `internal/config/**`, `internal/launch/**`, `internal/pr/**`, `internal/module/**`, `internal/termsafe/**`, `internal/privdir/**`, `internal/gitenv/**`, `internal/exec/**`, `internal/githubauth/**` and the rest of their imports, listed in `internal/surface/merge/builtin.go`). These are matched case-insensitively. A test derives the merge path's package closure with `go list -deps` and fails when a package in it is not refused.
6. **Approver.** `approvers` lists the approvers the policy accepts, and any one passing is enough. The one implemented is `cadence-review`; any other entry refuses at load. (`coderabbit` was dropped: it reviewed only 2 to 5 of the last 25 merged PRs per repository, and its findings live only in review bodies and its mentions are editable comments, so no rule over them could be made sound.)
   - **cadence-review:** reviews by `marker_author_id` (a `User`, state `COMMENTED` or `APPROVED`, `submittedAt` set) whose first line is exactly `<!-- cadence-review: <reviewer> head=<40 hex> crit=<n> imp=<n> -->` (no byte-order mark or leading space, lowercase hex, no leading zeros). Each `required_reviewers` name needs its latest marker to name the head, be posted at the head, and say `crit=0 imp=0`.
7. **Open findings.** Whatever approver passed, this fails closed. Every review by `marker_author_id` (any state, `DISMISSED` and `PENDING` included, at any commit), every PR conversation comment by it, and every inline review comment by it (a comment on a diff line, read from each review, in one page or the read refuses) whose body mentions the marker is an open finding for each reviewer it names, unless it is a strict passing marker at the head. A body mentions the marker when, with invisible, zero-width, bidi and control characters and invalid UTF-8 removed, NFKC-normalized, HTML entities decoded (then removed and normalized again), it matches `(?i)cadence[\s\\_\-‐-―−]*review\s*:`: a space before the colon, a Unicode hyphen or dash, a markdown escape or an entity does not hide one. A strict passing marker is a `User` review in state `COMMENTED` or `APPROVED`, never edited, whose first line is exactly the marker above, with no other mention in the body, `head=` equal to the review's commit and the PR's head, and `crit=0 imp=0`; a conversation or inline comment never is one. An open finding refuses unless a strict passing marker at the head by the same reviewer was submitted later (a marker in the same second does not count as later). A post counts at its last edit (`lastEditedAt`) when it was edited, so a finding edited after a pass is not cleared by it, and an edited post is never a pass, so an edit cannot turn a finding into one; an edited required-reviewer marker never satisfies the approver either. One naming a reviewer that is not 1-40 characters of `a-z`, `0-9` and `-` (`cadence-forge:code-reviewer`, say), with no parsable `submittedAt`, `createdAt` or `lastEditedAt`, or whose response did not carry `lastEditedAt` at all, refuses outright. Each reason names the review or comment URL and why it did not pass (CRLF line endings, a leading space or byte-order mark, a count of 10000 or more, `imp=01`, an uppercase head, a `DISMISSED` state, an earlier head). So `marker_author_id` is required whenever `mode` is `manual` or `auto`.

The boundary is the ADR's: anything on the operator's `gh` login, a misled worker included, can post a passing marker or edit the config and state files. The policy keeps the drain from merging by accident; it does not stop a worker that sets out to merge. The fixtures behind the tests are read-only captures of cameronsjo/forgectl#1204, #1203 and the #1199 checks (each review node later given `"lastEditedAt": null` and an empty inline comment list by hand); to run the reads against GitHub:

```bash
FORGECTL_MERGE_LIVE=1 go test ./internal/surface/merge/ -run TestLiveRead -v
```

### Merging

`surface merge <name> [--repo <path>] [--dry-run] [--json]` merges a worker's PR when the policy passes; the drain's autopilot (see [Drain](#drain)) runs the same code. One attempt:

1. Resolve `[surface.merge]` from the config file, and read the facts from GitHub with no cache, as status reads them. `Evaluate` must pass: mode `manual` or `auto` for `surface merge`, `auto` for the drain.
2. Take the PR title as the commit subject, only when it matches `^(fix|feat|docs|refactor|test|chore)(\([a-z0-9-]+\))?: [ -~]{1,72}$` (no `!`) and holds no issue reference (`#N` or `GH-N`) or issue or PR link (`github.com/<owner>/<repo>/issues/N` or `/pull/N`, in any case, with or without a scheme), which a commit on the default branch could read as closing it, and no CI-skip directive (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`, `skip-checks`), which would skip the default branch's workflows for the merge commit. Anything else refuses.
3. Read the PR and the check runs at the head again and refuse on any change since the verdict's read: its head, base branch, draft flag, state, any review, conversation comment or inline review comment (added, removed or edited), or any run of a required check (added, removed, or with another status or conclusion, such as a re-run at the head).
4. Write the audit attempt line (below). If it cannot be written, nothing is merged.
5. Run `gh pr merge <n> -R github.com/<owner>/<repo> --squash --match-head-commit <head> --subject <subject> --body <body>` through the host-pinned runner, from a new private temporary directory (never the worker's worktree or the caller's directory), never with `--admin` or `--auto`. The body is forgectl's own: the attempt line's hash (`Audit-line: sha256:…`), the policy hash, the head, the PR link, each required check run counted, each required reviewer's marker with its link, and a last paragraph `Merged-By: forgectl-cli` or `Merged-By: forgectl-drain`. No PR text but the subject is copied, so no closing keyword, `BREAKING CHANGE` or `Release-As` line reaches the default branch through it.
6. Read the PR back on a 30-second timeout of its own (so a merge cut short by its own deadline is still read): its state, merge commit and that commit's message, the default branch's head, and whether the merge commit is an ancestor of it (`compare` says `ahead` or `identical`), up to three reads 2 s apart (one when `gh` failed). Write the outcome line:
   - `merged`: GitHub says `MERGED` at the head, the merge commit is on the default branch, and its message carries this attempt's `Audit-line: sha256:…`.
   - `merged-elsewhere`: GitHub says merged, but the merge commit's message does not carry this attempt's `Audit-line`: something else merged it (`surface merge` by hand beside the autopilot, or the web UI).
   - `merged-unconfirmed`: `gh` reported success but GitHub does not say merged yet (a merge queue, if the branch has one, merges later with a message of its own), could not be read after it, says merged at another head, or the merge commit is not shown on the default branch.
   - `merge-failed`: `gh` failed and GitHub says the PR is not merged.
   - `merge-unknown`: `gh` failed or timed out, and GitHub could not be read after it; the PR may have merged, so check it by hand.

`--dry-run` stops after step 3 and writes nothing, not even an audit line. `--json` prints `{name, repo, dry_run, mode, result, pr, url, head, reasons, merge_commit, audit_line, audit_note}`, `result` being `merged`, `would-merge`, `refused`, `unreadable`, `merge-failed`, `merged-unconfirmed`, `merged-elsewhere` or `merge-unknown`. Exit 0: merged, or a dry run that would merge. Exit 1: refused, GitHub could not be read, the merge failed, could not be confirmed, was made by something else, or is not known; the message says which. Exit 2: a usage or setup error (no such worker, a row that records no GitHub repository).

`[surface.merge] mode` is `off` unless set. `manual` lets `surface merge` merge; `auto` also lets the drain, and waits for the Opus security review that plan task T10.4 names (ADR-0011, 2026-10-09 amendment, decision 7).

### Merge audit

`merge-audit.jsonl` sits in the surface state directory beside `queue.json`: two lines per merge (the attempt and the outcome) and one per refusal, appended under an flock on `merge-audit.lock` and synced, 0600 through the same pinned directory as the other state files. A line is `{time, actor, worker, repo, repo_id, pr, head, policy_hash, checks, markers, result, reasons, merge_commit, attempt, prev}`: `actor` is `cli` or `drain`; `worker` the worker's name; `policy_hash` the SHA-256 of the canonical JSON of the resolved policy; `checks` the required-check runs at the head tied to the PR; `markers` each required reviewer's latest marker (reviewer, link, head, counts); `attempt` on an outcome line the hash of its attempt line; `prev` the SHA-256 of the line before (`""` on the first). A refusal is not written when the most recent line about the same repository, actor and PR (for a refusal with no PR, `pr` 0, the same worker) is a refusal at the same head, with the same reason set and policy hash; any other line about it in between (a merge attempt, an outcome, another refusal) means the refusal is written again. A merge starts only when the file has room for its attempt line plus 8 KiB kept for the outcome line; otherwise the merge is refused (the audit file is full). The outcome line may use those 8 KiB.

`surface audit --pr <owner/repo#N> [--json]` prints that PR's lines through `termsafe` and checks the chain over the whole file, reporting the first line where it does not hold; exit 1 then, or when the file cannot be read, exit 2 on a bad `--pr`. `--json` prints `{pr, lines: [{line, hash, …the line's fields}], chain: {ok, lines, break}}`.

The chain detects accidental damage: a write cut short, a line edited or removed by mistake. It does not detect tampering by your own user, who can rewrite the whole file and every hash in it. What a rewrite cannot change is the default branch: each merge's squash commit body carries its attempt line's hash, and `main` refuses force-push. forgectl never prunes or rotates the file. It is read whole, up to 16 MiB; an append past that, or onto a last line with no newline, is refused, and so is the merge with it. To rotate it, or to repair a cut-short line, stop the drain, move the file aside (keep it), and start again: the new file's first line names `prev` `""`.
