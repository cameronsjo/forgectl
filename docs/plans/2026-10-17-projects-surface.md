## Design decisions

- Forgectl owns durable project, thread, and run identities. Herdr owns terminal processes, navigation, and presentation. Desk owns its existing human approval queue and supplies read-only progress views. Agent Board remains optional discovery/audit, not another execution authority.
- A project is a durable collaboration context, not a repository, workspace, or live process. It records an explicit working directory and a private team ledger. Multiple projects may use the same directory; matching a directory never authorizes reusing another project's workspace.
- A thread is a durable workstream within one project. A project has exactly one logical coordinator thread and may have worker threads. Thread IDs and roles survive replacement of their native harness sessions. Changing the coordinator's harness creates a new run of that same coordinator thread; it does not transplant native private history.
- A run is one explicit enrollment/process incarnation for a thread. Its identity is the mailbox's existing `RunID`, not a second competing execution ID. It records the selected harness, native session identifier when known, working directory, and optional validated surface reference. Retired runs remain visible. A claimed result, transport consumption, completed model turn, and independently verified output remain distinct.
- Use an explicit private registry root for the first slice, not a new global database or daemon. A locked, atomically replaced `registry.json` contains projects, threads, and binding history. Each project owns exactly one deterministic `<root>/<projectID>/team` ledger; shared or externally adopted ledgers are not supported. Keep the existing `projects` repository-inventory commands unchanged; expose collaboration under `surface project`. User-facing labels are not identifiers. Machine output includes schema version and exact IDs, and unsupported/malformed state is refused rather than rewritten.
- The project store is an index of logical identity and historical bindings, not a replacement mailbox. Current communication authority remains the enrolled mailbox roster. A saved run whose member/run/session no longer matches that roster is visibly stale, never silently repaired or considered live.
- Project/thread state and enrollment are separate durable resources. Binding only snapshots the exact member/run/harness/native-session/working-directory tuple; it never registers or replaces the roster. Compare-and-update under the registry lock requires the expected previous binding and prevents two threads claiming the same run within the project's ledger. Every subsequent action checks the tuple against the current roster and refuses stale state. A concurrent roster replacement can leave a stale snapshot, not a silently repaired enrollment. Read-only commands never register, replace, launch, focus, approve, create files, or narrow permissions.
- Project-controlled replacement uses a fresh RunID and refuses any previously bound run ID as a new incarnation. Same-RunID team registration is permitted only for an exact no-op or one-way missing-native-session to known-native-session enrichment with identical member, role, harness, endpoint, and working directory. Changing an already-known session or any other identity field requires a fresh RunID. The accepted Codex verifier needs this enrichment after creating its native thread; it is not process replacement. Lifecycle replacement settles/stops the owned old native process before re-enrollment; it cannot recall requests already in flight. Concurrent external roster edits are detected as stale/unknown, not treated as successful lifecycle changes.
- Preserve the existing worker worktree and launch-policy machinery when launching coding workers. Creating a logical thread alone creates no worktree, branch, process, or model request. Native resume/attach is capability-specific: unknown support is reported, never replaced by speculative terminal typing or a second concurrent writer to native history.
- Reuse the existing herdr sidebar/workspaces and tabs for navigation. Every bridge command requires an explicit named session, never the unpinned default client. Persist project/thread IDs outside herdr; display metadata is reapplied after reconnect and is never ownership evidence. Generated internal ownership markers must survive separately from user labels and runtime metadata; missing, changed, or duplicate markers cause refusal. Validate server incarnation plus exact workspace/tab/pane/terminal identity before acting. Never use cwd-only `workspace.open` to claim an existing workspace, or close a project workspace to stop one thread.
- Before a herdr mutation, persist its operation ID, expected server/parent identity, and `pending` phase. A complete verified reply or unique exact reconciliation moves it to `verified`; definite non-mutation becomes `failed`; incomplete/ambiguous evidence becomes `unknown`. Neither zero nor multiple matches after ambiguity authorizes another create/start. Post-server-restart tab ownership without durable evidence remains unknown. Retiring a binding does not itself terminate a process; explicit harness stop is capability-specific and unsupported stop leaves the surface intact.
- Desk displays a bounded, sanitized event projection, not raw prompts, credentials, native histories, or approval scripts synthesized from teammate messages. Its plain JSONL reader reports unknown process liveness; the integration must not turn that into a live/success claim. Human approval remains a separate, explicit Desk action.

Codex's implementation defaults are an explicit registry root, one private team ledger and coordinator thread per project, and one active enrolled run per thread. These minimize hidden shared state and reuse the already accepted replacement contract. A dedicated Rust Projects panel, a mandatory HTTP broker, a new scheduler, and automatic native-history conversion are excluded.

### First CLI contract

`surface project --root ABS create NAME --worktree ABS --json` creates one project and its unbound coordinator thread. `list --json` inventories that root; `show PROJECT_ID --json` returns its threads and binding observations. `thread --project PROJECT_ID create NAME --brief FILE --json`, `thread --project PROJECT_ID list --json`, and `thread --project PROJECT_ID show THREAD_ID --json` manage logical workstreams. `--brief` is optional and reads bounded plain text; no command interprets it as an instruction to the control plane.

Create accepts an optional `--instructions FILE` and snapshots bounded project instructions. P2 adds explicit `thread bind THREAD_ID --member NAME --run-id ID --expect-run ID|none`; `--expect-run` is mandatory. Binding never launches or registers a process. Machine responses carry `version`, registry `revision`, exact project/thread IDs, role, historical run bindings, and separate enrollment/native/surface evidence. Missing-root list returns an empty list without creating it; show or mutation against an unknown ID fails. Unknown commands and missing IDs never fall through to an interactive picker.

P1 implements only the creation and inspection commands. Native launch/open/focus/stop command contracts follow the verified P3 capability seams, not guessed uniform flags.

P1 uses `internal/surface/project` for the versioned registry and `internal/cli/surface_project.go` for its CLI. The registry is capped at 4 MiB; names at 128 UTF-8 characters without control characters; project instructions and thread briefs at 16 KiB each. Project creation atomically includes one unbound coordinator thread. Creation allocates no model/native process, worktree, or branch; the deterministic team directory is created only when explicitly enrolling later. A shared `privdir.OpenFileChecked` sibling reuses existing descriptor-relative ownership, type, link-count, and identity verification but rejects wrong modes rather than repairing them. Existing `OpenFile` behavior is unchanged. Root validation uses the existing base/leaf pinning contract, including its documented trusted ancestor-placement boundary, not a claim that every filesystem ancestor is authenticated.

The registry stores logical identity and bounded context only in P1, not speculative herdr fields or native liveness. P2 introduces immutable run binding snapshots/history plus capability-specific native observations. Enrollment status (`unbound`, `current`, or `stale`) is separate from missing native evidence and unknown process liveness.

P2 binding snapshots never update automatically. An explicit repeat bind of the active RunID may fill an empty native-session field once, with an exact match of every other identity field; a known native session never changes within a run. Until that explicit refresh, a changed roster tuple is stale. Project membership comes from the deterministic private ledger, not a shared working directory: a worker may have its own Git worktree, whose exact path is captured in the binding. Standalone team registration rejects current-member RunID collisions; the project's history additionally rejects historical RunID reuse. These are same-user consistency guards, not authentication against manual state edits.

## Requirements and acceptance

1. Project and thread IDs MUST survive fresh CLI processes and native-session replacement. Two projects using the same working directory MUST remain distinct. A thread MUST belong to exactly one project; run identities MUST not be rebound to another thread.
2. State MUST be versioned, size-bounded, owner-private, and updated under a lock with atomic replacement. Unknown versions/fields, malformed or duplicate identity, duplicate JSON keys, trailing data, symlinks, hardlinks, public state files, and conflicting updates MUST fail without overwriting the original. Read-only operations MUST leave a missing store absent and preserve modes/bytes of rejected files.
3. A project MUST have exactly one coordinator thread. A new thread MUST NOT acquire tool permissions or communicate until explicitly enrolled. Run replacement MUST retain the historical run and reject stale mutation attempts.
4. Existing mailbox state MUST remain authoritative for communication. State inspection MUST distinguish unbound, current enrollment, stale enrollment, and missing native/surface evidence. It MUST NOT infer native liveness from a roster row or display token.
5. Herdr actions MUST target an explicit named, task-owned test session during acceptance. An ambiguous create/launch acknowledgement MUST become a visible recoverable state rather than an automatic duplicate launch. Reconnection MUST not reuse IDs from another server incarnation.
6. The first UI MUST reuse existing navigation and Desk rendering. Selecting a thread MUST focus its verified current surface or explain why it cannot. Native attach/resume MUST preserve that harness's permission posture and private history ownership.
7. A live project MUST support a real cross-harness task, a coordinator harness replacement, and recovery after closing/reopening the control UI. The same logical project/thread IDs and artifact provenance MUST survive. An unrelated project/session MUST remain unchanged.
8. All model traffic in this authorized implementation/acceptance MUST remain direct OpenAI. Claude is deferred; unsupported harness capabilities MUST be explicit. The project launch path MUST verify its explicit provider/posture policy and native selected provider instead of inheriting arbitrary command arguments, credentials, fallback providers, or global model defaults. No authentication refresh-token copy is permitted. This task constraint does not authorize changing unrelated generic launcher defaults globally.
